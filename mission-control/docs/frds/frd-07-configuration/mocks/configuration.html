DR-048 · where a project's Pandacorp files live (the .pandacorp/ integration layer) and how a project's overlay is kept current (overlay versioning + auto-upgrade)STRUCTURE: a project keeps the factory-integration layer in a single `.pandacorp/` folder (the project's analogue of .github/), SEPARATE from the product. Committed (English, a clone needs it): `.pandacorp/{guide.md,status.yaml,idea-origin.md,README.md,verify.sh}`. Gitignored (Spanish/owner-facing/runtime, regenerable): `.pandacorp/comms/` (summary, iteration, progress, activity), `.pandacorp/inbox/` (bugs, decisions), `.pandacorp/run/` (skill-active marker, caches). Owner chose SILENT for compatible (same-MAJOR) bumps; a breaking (MAJOR) jump is announced first. Rules:

  1. Architecture — two layers, never fused (DR-049):
    • Platform architecture (docs/product/architecture.md, stable, ONE per project): chosen stack (golden path A/B/C/D and why — see DR-002), high-level architecture (text/mermaid diagram), data model (complete schema), deploy strategy, cross-cutting concerns and service boundaries.
    • Per-FRD blueprint (docs/frds/frd-NN-<slug>/blueprint.md, one per FRD): how THIS feature is implemented on top of the platform — its components CMP-NN-<slug> and interfaces IF-NN-<slug>, API/action contracts and feature-specific external integrations (APIs, limits, costs), each traced to the FRD's REQ-NN-MMM. It references docs/product/architecture.md rather than re-describing the platform, and its header restates the source-of-truth hierarchy FRD > FDD > design-tokens > blueprint > work order. Large feature → promote blueprint.md to a blueprints/ folder split by coherent concern (NOT "pillars"). A single global docs/blueprint.md is an anti-pattern — never produce one.
  2. Stack: start from the recommended one (factory/standards/stack.md) at the latest stable versions. It's a suggestion: if for THIS project there's a better technology/library/language, propose it with clear trade-offs. The choice is approved by the owner in the blueprint (DR-002) and recorded as an ADR. The durable conventions (factory/standards/: structure, quality, patterns) are NOT negotiable.
  3. ADRs (docs/adr/adr-NNN-<slug>.md): one for each non-obvious platform-level decision (cross-feature). Format: context, decision, discarded alternatives, accepted trade-off, agent/model that decided.
  4. Design for one-person operation: managed services over self-hosted, Postgres for everything that can use it, no microservices, no Kubernetes, minimal monthly cost (ideally $0 at launch). For external services (storage, email, payments, analytics), account model and secrets, follow factory/standards/external-services.md (only approved MVP services, provider-specific account/environment reuse and dated preparation evidence; DR-035..038/134).
  5. Security from the design: where the secrets live (SOPS+age store + the approved three-file environment handoff, see external-services.md), what personal data is touched (minimize it), rate limiting on public endpoints.
  6. Every FRD's REQ-NN-MMM must be traceable to blueprint components (CMP-NN-<slug>/IF-NN-<slug>) in that FRD's blueprint.md. If an FRD cannot be fulfilled with the design, flag it instead of improvising.
  7. Coarse work orders + a Build Plan (per-FRD, at docs/frds/frd-NN-<slug>/work-orders/, DR-050):
    • Coarse slices: break each FRD into a HANDFUL of slices — each a cohesive view / page / capability (e.g. not "registration endpoint that validates email format", but "full auth view: registration + login + session flow"), NOT atomic components. Enough context to build the slice end-to-end, small enough to review on its own (atomic WOs multiply per-slice overhead — a primary cause of slow, expensive builds).
    • Calibrated size band (DR-100, 2026-07-01): target ~25–50 min of build / ~1.5–4k LOC per WO; SPLIT above ~4k LOC (rejects escalate superlinearly past it); FOLD a <~20-min slice into a sibling (the FRD gate's fixed ~9-min cost makes it >100% overhead).
    • The Build Plan lives in the FRD's blueprint.md: the DAG of its work orders (order, intra-/cross-FRD deps, what runs in parallel, integration order) — the build engine READS it instead of re-inferring dependencies at runtime.
    • Disjoint artifacts (DR-060): every work order MUST declare artifacts: [globs] (the files/dirs it writes) in its frontmatter, and the Build Plan records each WO's artifacts so the plan is verifiably disjoint within a wave. Design wave-parallel WOs to have non-overlapping artifacts — never split one module across sibling WOs that build in the same wave (parallel implementers collide); merge them into one coarse WO or serialize them with a dependency. The engine enforces disjointness from the declared artifacts (it serializes any overlap into a later wave), but the plan should be disjoint by design.
    • The API contract is per-WO at docs/api/<wo-id>.md (listed in that backend WO's artifacts), not a single shared docs/api.md.
  8. Consult the factory memory first (factory/memory/, DR-047): read factory/memory/INDEX.md FIRST (one line per active lesson with its "use when" trigger), open the full lesson files whose trigger matches, then Grep the store by domain/tags for active library-verdicts (prefer what worked, avoid what failed) and for gotchas/anti-patterns in this domain. If you choose against a verdict, justify it in the ADR. When a lesson materially informed a choice, CITE its LESSON-NNNN in the ADR/blueprint — the close-out's count-lesson-citations.sh counts citations and updates times_applied/applied_in deterministically; NEVER edit those counters by hand (loop v2). The store is the factory's accumulated experience — use it so you don't relearn the same lesson.

verify.sh runs in a clean environment, parses fail-closed (ambiguity = failure), does not expose to the generator agent the exact names of the tests to pass nor the fixtures, and emits actionable messages (which rule failed and why). Applies to the verify.sh template that the blueprint creates

DR-020operation of the construction (how implement runs unattended)Auto

implement launches a dynamic workflow in the background and runs in auto mode (permissions; the owner enables it at the user level, the repo does not grant it). Freeze-on-red: a stage that fails throws → the pipeline skips that WO (does not commit what is broken, leaves HEAD at the last green, marks it BLOCKED, notifies) and continues with the independent WOs. Circuit breakers (cap on iterations, no-progress, workflow budget). The workflow stops by itself when the queue is empty; to run continuously it is wrapped in /loop self-paced. The operator talks through files (the unified change queue .pandacorp/inbox/changes/ via /pandacorp:change — DR-069 —, .pandacorp/inbox/decisions.md, rethink_pending), which the ENGINE reviews at every safe point (FRD boundary)

PARTIALLY SUPERSEDED: the per-WO freeze framing predates DR-050 (coarse WOs, per-FRD gate) and DR-073 (patch-first); the inbox channel was unified by DR-069; the safe-point drain is in-engine since audit-20 (2026-07-01). Kept for the still-current parts (auto mode, freeze-on-red principle, circuit breakers); read DR-050/069/073 for the current mechanics.

DR-021database and services in developmentAuto

in DEV, each project and each worktree brings up its DB/services with Docker Compose, its own port; in STAGING/PRODUCTION, the golden path's managed DB (Neon — chosen over Supabase, see external-services.md), never Docker. See factory/standards/infra.md

DR-022port assignment (several projects/worktrees in parallel)Auto

dev ports are ALLOCATED from a central ledger (factory/ports.yaml, gitignored), NEVER guessed or hashed (hashing collides by the birthday problem): scaffold reserves the next free 10-wide block from base 4000 (slug→base recorded in the ledger + dev_port_base in the project's status.yaml) and a project keeps its block forever; within the block, offsets keep worktrees apart (app agent +0 / review +1, Postgres +2/+3, Redis +4/+5, +6..+9 spare); blueprint materializes the ports into .claude/launch.json (app=base+0) and the worktree .env; in Docker, a different Compose project name per worktree. Zero collisions by construction. See factory/standards/infra.md

DR-023test the progress without stopping the constructionAuto

the owner tests the last independently verified snapshot (last_green_sha) in a separate git worktree (a single review folder, refreshed to the latest green), never the agent's working tree. The gate publishes it with two commits: A is the reviewed snapshot; metadata-only B writes last_green_sha=A + safe_to_test only after proving A exists and is an ancestor of HEAD (BL-0066). A commit can never contain its own SHA, so amend/self-hash publication is forbidden. Native checkpoints do NOT work as a snapshot (they ignore what was done by Bash)

ObligatorioProgramaciónlint/CI

API design

Domain: Programming · Severity: MUST in API/service-type projects (stacks B/C; also route handlers of stack A). Enforcement: lint/CI. See DR-028.

Rule — error contract (RFC 9457)

  • HTTP errors return application/problem+json (RFC 9457, which obsoletes 7807) with the 5 members: type (default about:blank), title (stable except for i18n), status, detail, instance.
  • Validation errors with a custom extension errors[] of {detail, pointer} (RFC 9457 allows extensions; this is NOT normative). pointer = JSON Pointer (RFC 6901).
  • Shared problem() helper in the golden path (Next Route Handlers + Python APIs).

Rule — REST

  • Well-named resources, /v1 versioning, pagination, standard HTTP codes.
  • Validation at the boundary before the logic (Zod / pydantic), which generates these error bodies consistently. (Reuses the boundary-validation convention from conventions.md, defining its output.)

How it is verified

  • verify.sh gate (stack A): a route handler returning 4xx/5xx without the shared problem() helper is RED (fail-closed grep gate; vacuous without API routes). The helper (src/lib/problem.ts) ships as a canonical snippet in stack-a-nextjs/STACK.md. Canaried by canary.sh (DR-079).
  • REST conventions (resources, /v1, pagination, codes): reviewer correctness lens (review-only).
  • Contract-level assertions (required members present, content type) live in the FRD's integration tests when the feature IS an API (test-writer generates them from the EARS criteria).

Why

A standard, machine-readable error contract makes clients (and other agents) handle errors uniformly, instead of ad-hoc strings per endpoint.

Sources: rfc-editor.org/rfc/rfc9457
