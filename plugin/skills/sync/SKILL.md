# /pandacorp:sync

**The reverse flow: "I changed the code by hand — now catch the docs up, completely."** The whole pipeline runs `doc → code` (`spec → design → architecture → implement`, and day-to-day `change`/`iterate`). `sync` is the inverse: you edited an app directly — to go fast, to see it change live — and the code outran the docs. `sync` propagates that reality **upstream** to the owning canonical docs **and** the area's decision log. It is `iterate` run backwards, and it is **exhaustive** — the owner's standard is *lots of well-made documentation over too little; nothing slips through*.

**The inverse flow inverts the oracle (read this — it's the whole design).** Forward, the **doc is the oracle**: code is validated against the FRD. Here the **code becomes the oracle** and the doc conforms to it (constitution §24). So `sync` **cannot verify a change is correct — only describe what the code DOES.** Hence: (1) an **intent gate** — only you know whether what's in the code was *deliberate* (document it) or *a half-finished experiment / accident* (don't bless it); (2) **provenance** — every doc it writes is marked *reconciled-from-code* (like `adopt`'s as-built), never dressed up as authored design intent.

> **Preflight (DR-045) — modo proyecto.** This skill writes to the project's docs, so first confirm the marker `.pandacorp/status.yaml` exists. If it's missing **but** you're at the factory root with hand-edits under `plugin/` or `factory/`, this is *modo fábrica* — out of v1 scope: route the owner (in Spanish) to `/pandacorp:learn` (durable know-how, which already versions the plugin) and stop. If it's missing entirely, this folder isn't a factory project — `/pandacorp:adopt` brings one in, `/pandacorp:spec` creates a new one. Then, if `overlay_version` in `.pandacorp/status.yaml` is behind the plugin's `OVERLAY_VERSION`, run `/pandacorp:upgrade` first (silent for compatible bumps, DR-048) — **but if a build is running (`running: true` + fresh `supervisor_heartbeat`) do NOT run `/pandacorp:upgrade` mid-build: it must never regenerate the engine/gates under a live build (its own active-build guard also refuses).** When the owner reaches this skill directly mid-build, route them to `/pandacorp:change` (the queue) instead of mutating docs concurrently.

`$ARGUMENTS` (or the conversation): optionally what you changed by hand (e.g. `/pandacorp:sync "puse el botón de descartar en rojo y rehíce el header del card-detail"`) or a change-card slug to close out (e.g. `/pandacorp:sync --close-out <slug>`); empty (`/pandacorp:sync`) lets it find the changes itself — including, with no context at all, a full audit.

## Modes: reconciliation (warm/cold) vs close-out

The two below are open-ended **reconciliation**: they find divergences and propagate the full cascade. **Close-out is different in kind** (a bounded, one-card batch closure of a change already known to be correct) and has its own section below, instead of following Steps 1-8.

- **Warm** — the changes are already in this conversation. Start from them, **but still verify against the real code** (don't trust the chat's memory of what changed; read the diff).
- **Cold** — no context (a fresh conversation, or hand-edits made long ago and never documented). Run a **FULL AUDIT**: enumerate every surface of the app from the code — routes, components, the data model, APIs, business logic — and compare each to its owning doc; the "change set" is the set of **code↔doc divergences (gaps)**. For a large app, **fan out** (a reader per area: features/UI / data+architecture / build state) and consolidate. The bar is **find every gap — nothing passes unnoticed.**

## Mode: close-out

**Batch-closes ONE already-implemented change** (a queue card the owner edited in by hand, a `/pandacorp:change --now` subagent left ready, or a direct session just finished), with documentation **proportional to its rigor** instead of the warm/cold full cascade (proposal 37 §A.6/§A.8). No intent gate: the change is a known, deliberate fact, there is nothing to sort into bug/pending/accident.

1. **Inputs.** The card (`.pandacorp/inbox/changes/<slug>.md`) and its `rigor`. Missing `rigor` → derive it (`plugin/scripts/classify-change.sh --repo . --range <base>..HEAD`, or `--worktree` for an uncommitted change) and write the verdict back. Note the sha/diff and, if named, the affected work order.
2. **Precondition: refuse, don't degrade.** `.pandacorp/run/gate-report.json` must be recent — written after the branch's last commit (compare its `at` with `git log -1 --format=%cI`) or less than 30 minutes old — `green: true`, `scope` ∈ {full, since} (never `partial`); missing, red, partial or stale → refuse and name the exact gate to run. `running: true` with a fresh `supervisor_heartbeat` → refuse too (the engine is the sole writer while it runs).
3. **Set `status: closing`.** Stamp the card with `status: closing`, `implemented_sha`, `closing_at` (ISO timestamp) BEFORE writing anything else, so an interrupted run stays visible instead of vanishing (`doc-lint.sh` reds a `closing` card older than 48h, unconditionally: a stuck close-out is a build-safety defect on ANY project, not doc-spine drift to tolerate).
4. **Write the artifacts for the card's rigor tier:**
   - **micro**: card → `done/` with `shipped_sha`/`shipped_at`; one line in `.pandacorp/comms/progress.md`; a `docs/decision-log.md` entry ONLY if `supersedes:` is non-empty.
   - **normal**: the above, PLUS the affected WO's `## Status Note` + `implementation_status` (or a minimal new WO from the template if none fits), a `docs/decision-log.md` entry always, and the `status.yaml` rollups. **No owning FRD/WO at all** (BL-0163 §S4.5 — e.g. Manual/content prose with no `REQ-NN-MMM` trace to any feature): do **not** fabricate a synthetic WO to satisfy the bullet above — a placeholder WO with invented requirements pollutes the real traceability spine for every genuine FRD. Instead, record the change and why it has no owning WO directly in the `docs/decision-log.md` entry (already required at this tier) and skip the WO Status Note; this is the deliberate exception, not a silent gap.

   - **critical**: refuse ("critical changes go through `/pandacorp:implement`") unless the owner explicitly passes `--force-critical`; then do the `normal` set PLUS the full cascade (FRD/blueprint/ADR as it applies), marked `reconciled-from-code` exactly like cold mode. The close-out commit message must quote the owner's literal sentence authorizing it.
5. **One commit.** Code (if not committed yet) and docs land together, Conventional Commits, `(WO-…)` when applicable, citing the card. Code already committed → a separate `docs(<scope>): close-out <slug>` commit.
6. **Finish or fail honestly.** On success, clear `closing` (the card is now in `done/`, its rigor already covers this). Mid-way failure → leave the card `closing` with a note of exactly what landed and what's missing; tell the owner the same, in Spanish.

## Steps (warm / cold reconciliation)

1. **Detect context, pick the mode** (warm vs cold, above). You're in *modo proyecto* — Mission Control or a product app.
2. **Build the change set.** *Warm:* the uncommitted working tree (`git status`/`git diff`) + commits since the last one that touched `docs/decision-log.md` (or since `last_green_sha`) + what's in context. *Cold:* the audit's gap list. Either way **read the real code**, not just file names — you need *what behaviour / look / architecture / scope changed*, not which lines moved.
3. **Classify each divergence — DIRECTION FIRST, then the cascade (the key step).**

   **Phase A — direction.** Decide which side is right *before* deciding what to write, because only one direction gets documented:
   - **Code has MORE than the doc** (behaviour the doc doesn't describe) → the code outran the doc → **document it** (the cascade below).
   - **You changed the behaviour ON PURPOSE**, the old doc no longer applies → the intent moved → **update the doc** (you confirm this at the intent gate, step 5).
   - **The doc has MORE than the code** (the doc specifies something the code doesn't do) → **do NOT rewrite the doc down to the broken/absent code** — that would bless a bug or erase wanted work. **Route it, don't document it:** a **bug** (code contradicts a doc that's right) → file via `/pandacorp:change`/`bug` to fix the CODE, the doc untouched; **documented-but-unbuilt** (a wanted feature never implemented "por diferentes motivos") → mark it **pending** (the PRD feature-landscape / the work order's `implementation_status`), the spec untouched.

   **Phase B — cascade.** For what IS to be documented (the code outran the doc, or a deliberate change), expand its **full cascade** — don't stop at the top doc:
   - **behaviour / feature** → the owning **FRD** (`docs/frds/frd-NN-<slug>/frd.md`) **and almost always its work order(s)** (`work-orders/wo-*.md` — a behaviour change not reflected in the WO leaves the build's own record false) **and its `fdd.md`** if the UI moved. Behaviour with no FRD → a **new FRD module** (frd + blueprint + work-orders, + fdd/mocks if UI; numbering continues).
   - **architecture / data model / stack / a tech choice** → the feature **`blueprint.md`** **+** an **ADR** (`docs/adr/`) **+** `docs/product/architecture.md` **+** the affected **work orders**.
   - **UI / interface / interaction** → the feature **`fdd.md`** **+**, if it touched the shared system, **`DESIGN.md`** / `docs/design/design-tokens.json` / `docs/design/components.md`.
   - **product scope / goal / metric** → the **PRD** (`docs/product/prd.md`, the feature-landscape).
   The source-of-truth hierarchy (FRD > fdd > tokens > blueprint > work order) decides who *wins* a conflict; the **cascade** decides what you *touch* — update the owning doc **and** every derived doc the change made obsolete.
4. **Sweep BOTH trees — `docs/` and `.pandacorp/`.** Beyond `docs/`, refresh the `.pandacorp/` text layer the change affects: `comms/summary.md` (the Spanish project narrative), a line in `comms/progress.md`, `comms/iteration.md` if a manual phase was in flight, and the `status.yaml` counters. Neither tree is left stale.
5. **Present the sync plan → INTENT GATE (the owner judges intent, not correctness).** Show, in Spanish, a tight "this changed → I'll do X" list (for a cold audit with many gaps, group them by doc). The owner sorts each divergence into ONE action: **document** (real behaviour the code outran the doc on) · **update the doc** (a deliberate behaviour change — the old spec no longer applies) · **it's a bug** (the doc is right, the code is wrong → file via `/pandacorp:change`/`bug`, the doc stays) · **pending** (documented but never built → mark not-built, the spec stays) · **experiment / accident** (don't bless — leave it, or flag to undo). **This gate is the independent oracle the skill lacks** — and the only place a bug can be told apart from an on-purpose change, which the code alone can't reveal. Confirm before writing.
6. **Write the whole cascade — marked reconciled-from-code.** For each blessed change, write **every** doc in its cascade (step 3) across both trees (step 4). Header reconstructions *"Reconciled from code by `/pandacorp:sync` on {{DATE}} — describes existing behaviour, not a forward plan."* Re-use the doc templates (DR-077) for shape. Product docs in **English** (committed); the `.pandacorp/comms/` layer in **Spanish** (gitignored) — the language rule (DR-009). Don't invent rationale; a stub with a TODO is more honest than a confident fiction.
7. **External design source — Claude Design (DR-058).** A design system can have an external mirror: if the project's design came FROM / was pushed TO a Claude Design project via `/design-sync`, `docs/design/` carries a `_ds_manifest.json` (or a recorded projectId). If **this** sync changed the shared system (tokens, a shared component, the inventory) **and** that provenance exists, the Claude Design project is now **stale** → handle it like the Manual: **detect → flag → OFFER, never auto-push.** Tell the owner (Spanish) it diverged and offer to re-sync via `/design-sync` (incremental, one component at a time). **Don't push automatically** — it's an outward-facing write to an external beta service that needs the owner's claude.ai login (a human gate); the repo's `docs/design/` stays the source of truth (DR-054). No manifest ⇒ nothing to sync; skip silently.
8. **Decision log, lint, commit, report.** Record the two-layer entry in the area's `docs/decision-log.md` (date · **What** · **Why** · **Impact** = which docs you touched; most recent on top) — **the diff has the *what*, not the *why*: ASK the owner the why.** Refresh `status.yaml` carefully (bump `updated_at`; read, don't invent — the pending-change count is DERIVED from the queue directory, never stored: DR-115). Run `.pandacorp/doc-lint.sh -v` as a safety net. Capture any durable lesson (DR-047) / owner fact (DR-053) that surfaced. Commit in English, conventional, touching the canonical docs **and** the decision-log entry together. Report in Spanish: everything propagated, where, and any gap left open.

## Rules — the invariants (the operative detail is in the Steps)

- **Documents, never verifies (the inverted oracle, intro).** Correctness is judged by the owner at the intent gate (step 5); mark everything reconciled-from-code, never authored intent.
- **Never degrade the spec.** Document what the code does in EXCESS; where the **doc is right**, route it — a **bug** → `/pandacorp:change`/`bug` (fix the code), a **documented-but-unbuilt** feature → mark pending — and leave the FRD/PRD untouched (step 3, Phase A). Only a confirmed deliberate change rewrites the spec.
- **Exhaustive within the diff, bounded to it (DR-012).** Propagate each change through its **whole cascade** (step 3, Phase B); *nothing slips through* — but don't touch docs the change never reached, and don't inflate.
- **Two layers, always (the `CLAUDE.md` rule).** Owning canonical doc **+** area decision-log entry, same commit, before the turn closes — never one without the other (step 8).
- **The "Why" isn't in the code — ask the owner** (step 8); never fabricate rationale.
- **Both trees, each in its language (DR-009):** `docs/` in English (committed), `.pandacorp/comms/` in Spanish (gitignored) — neither left stale (step 4).
- **External mirrors: detect + offer, never auto-push** (step 7).
- **Close-out is proportional, never degraded (proposal 37 §A.6).** Rigor decides HOW MUCH gets written, not WHETHER; a `critical` card refuses without an explicit owner `--force-critical`; the `closing` state plus doc-lint's unconditional 48h check keep an interrupted close-out visible, never silently lost.
- **Modo proyecto only (v1):** plugin/factory hand-edits go to `/pandacorp:learn`.
- **`status.yaml` is read, not hand-authored (DR-050);** commits conventional + English, direct to main is fine, never force-push.
