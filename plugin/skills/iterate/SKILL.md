# /pandacorp:iterate

Internal continuous-iteration engine reached through `/pandacorp:implement`, the single owner entry for building or resuming any feature, change or bug. Runs IN the project. `$ARGUMENTS` (or the conversation): what you want to add/change (a new FRD, an adjustment like "sort the list", a fix).

> **Preflight (DR-045) — is this a Pandacorp project?** This skill mutates the project, so first confirm the Pandacorp marker: `.pandacorp/status.yaml` exists. If it's missing, STOP and tell the owner (in Spanish) that this folder isn't a factory project yet — `/pandacorp:adopt` brings an existing project in, `/pandacorp:spec` creates a new one. Then, if `overlay_version` in `.pandacorp/status.yaml` is behind the plugin's `OVERLAY_VERSION`, run `/pandacorp:upgrade` first (silent for compatible bumps, DR-048) — **but if a build is running (`bash "${CLAUDE_PLUGIN_ROOT}/scripts/check-build-liveness.sh" .pandacorp/status.yaml` returns `RUNNING`, including a fresh fenced lease; malformed leases fail closed) do NOT run `/pandacorp:upgrade` mid-build: it must never regenerate the engine/gates under a live build (its own active-build guard also refuses).** Run only for the CLI-selected scope in its docs unit on `lane/<run_id>/integration`. A new request during a live build becomes a `status: draft` card validated with `node "${CLAUDE_PLUGIN_ROOT}/scripts/pandacorp-build.mjs" card check .pandacorp/inbox/changes/<slug>.md`, never a concurrent edit to that build's plan. Don't proceed or invent docs over a missing structure.

The queue is a file format with readers, not a build entry. "Anótalo" writes a draft card with cited **Dentro**, **Fuera** and **Dudas**, validates it with `card check` and stops. "Impleméntalo" follows `../implement/references/engine-v2.md` to capture/validate the conversed scope and run detection/preflight. An explicit card target builds that card only; a bare invocation builds the pending plan. Never drain unrelated cards.

## Steps

1. **Understand the change** and its context (read PRD, FRDs and current state). Resolve scope questions before starting the run; mid-run doubts follow the `implement` autonomy protocol.
2. **Impact triage (the PM/architect prepares only the selected scope; the CLI decides size and execution).** What the owner asks for is high-level; your job is to decide what documentation to change/create and tell them which case it falls into:
   - **Small adjustment / fix** → if the change **extends an existing work order** (e.g. add pagination + filters to an already-`VERIFIED` "product list" WO), **reopen it**: set `implementation_status: PLANNED` in that work order's frontmatter and widen its In-Scope + `## Summary` (BL-0015 — keep the one/two-line "what this builds" current with the new behavior; Mission Control's board reads this section verbatim) + `## Status Note` with the new behavior. If it's genuinely new, add a new **coarse** work order under the affected feature's `docs/frds/<frd>/work-orders/`, with its own filled `## Summary`. Update the owning FRD acceptance criteria when behavior changes. These changes belong to the CLI docs unit and its selected work orders; they never add work to another live run.
   - **New feature / module** → bounded mini-pipeline: **delegate research to the `researcher`** (research in depth if it's a new module), the `product-manager` creates a **new FRD module** (`docs/frds/frd-NN-<slug>/`, numbering continues — `frd.md` + per-feature `blueprint.md` + `work-orders/`, plus `fdd.md`/`mocks/` if it has UI; nothing else moves), the `architect` writes that feature's `blueprint.md` referencing `docs/product/architecture.md` (+ an `adr/` entry if it touches the platform), and the feature's **work orders** are generated under `frd-NN-<slug>/work-orders/` (via `work-orders`, each with a filled `## Summary`, BL-0015). If it brings new UI, a mini design step (`/pandacorp:design` bounded, same global design tokens).
   - **Fundamental change** (architecture, DB engine, data model — impacts what's already built) → **during scope planning, show the owner the impact radius BEFORE touching anything**: which FRDs/work orders are affected, what has to be redone/migrated, approximate cost. If they confirm: **a platform `adr/` entry that replaces the previous one** + adjustment of `docs/product/architecture.md` and of the affected features' `blueprint.md` + work-order re-planning, and re-plan only after any current build releases ownership at a safe point. Never set `rethink_pending` or edit `status.yaml` by hand. A new PRD or several epics requires the internal `new-version` planning engine before construction, not an ordinary run with expanded scope.
2b. **Supersession-completeness check (DR-116) — only when this change REPLACES an existing rule/claim, not when it only adds.** If the change carries a `supersedes:` declaration (from the selected scope card) or the triage in step 2 replaced a stated rule/limit/default/AC/data-model fact, verify the supersession is **COMPLETE before** returning the docs unit — this never blocks the change, only an incomplete propagation of it: (a) derive the owning-doc set (the doc that owns the fact per `documentation.md`'s canonical-doc table + its cross-refs); (b) `grep` the OLD claim's key terms across `docs/` + `.pandacorp/` to build a candidate list; (c) read ONLY the candidates and confirm **no doc still asserts the old claim** (excluding append-only dated `docs/decision-log.md` history, DR-093) AND the **why is recorded** (canonical doc updated + a `docs/decision-log.md` entry — the two-writes discipline). Any survivor of the old claim, or a missing decision-log entry, is **reported back and closed in this same change** — that is the fix, not a veto. Canonical: `factory/standards/document-consistency.md`.
2c. **Test-side supersession — never split a derogation from its re-bless across a `dependsOn` edge (BL-0051).** 2b covers the DOC side of a supersession; this is its TEST side. When the change makes a work order **derogate a contract that an existing BLESSED reviewer test asserts** (any reopened/already-VERIFIED FRD whose contract you are intentionally superseding — an SSOT split, a changed signature/shape, a redefined default), decompose so the **re-bless never depends on the derogating WO**: (a) fold the derogation AND the re-bless of that test into the SAME work order, or (b) place the re-bless in a work order that does NOT `dependsOn` the derogating one — both then build in one wave and the FRD gate judges the recomposed feature against the re-blessed contract. The forbidden shape is `WO-B (re-bless) dependsOn WO-A (derogates)`: the blessed test asserting the OLD contract blocks WO-A, and WO-B can't run until WO-A verifies — a circular deadlock (LESSON-0104). Name in the derogating WO's Summary/Status Note WHICH blessed test file encodes the superseded contract, so the gate's reviewer can prove the derogation was declared. **DR-080 is untouched:** the implementer never edits a blessed test — the re-bless is authored by the reviewer role.
3. **Link the work back to its card (DR-147).** When this integration runs for an explicitly selected card, every work order it creates or reopens carries `source_change: [<slug>]` in its frontmatter (append to the list if the WO already names another card). That link is what lets `change-reconcile.mjs` close the card the moment those WOs are VERIFIED, through whatever door they get built — the engine, a direct session or a launch plan.
3b. **Return the plan to the CLI**: create/update work orders under the affected feature's `docs/frds/<frd>/work-orders/` in the assigned integration worktree. Return the docs unit report through the `implement` session protocol; the CLI commits it and runs the selected work. Do not launch another build recursively. The CLI owns build state, work-order transitions and project phase; never edit `.pandacorp/status.yaml` by hand or commit in the main checkout.
4. **Regression**: existing tests must stay green. Every fix records the bug in `.pandacorp/comms/progress.md` and adds a tests-first regression case anchored in it (DR-015). Independent review and the CLI gates determine completion; production landing remains an owner gate.

## Rules
- **Logical model freshness (DATA-7):** model-changing iterations MUST include `docs/product/data-model.json` in the schema-owning work order's declared scope and same change/commit. Follow the always-injected `logical-data-model.md`; update canonical docs and the digest when their facts change, and require the independent reviewer to compare actual schema definitions with published attributes/keys/mappings/cardinalities before closure. An unchanged logical shape needs recorded evidence, not JSON churn.
- **One owner door plus `decide`.** `/pandacorp:implement` builds/resumes the explicitly selected scope; `/pandacorp:decide` answers something the build asked. `iterate` is hidden (`user-invocable: false`) and only prepares canonical documentation for the selected scope; it never drains the queue.
- It does NOT bump any version field. Day-to-day iteration is versionless; `release` derives the semver tag from conventional commits. A formal milestone with its own mini-PRD uses internal `new-version` planning through `implement` before a build starts.
- Keep the scope bounded to what was requested (DR-012). Don't take the chance to rewrite more than needed.
- Conventional commits in English with scope are made by the CLI on the integration branch. Merge-queue is the only path to main; never force-push.
