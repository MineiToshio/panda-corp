# Freeze and fidelity hand-off (Steps 7 to 9)

The goal: the build has everything it needs to reproduce the approved design, and a way to measure the difference. In order:

1. **Typography is web fonts.** If the prototype still uses system stacks (`system-ui`, `Iowan Old Style`, `Segoe UI`…), it renders differently on every operating system and in CI screenshots. Render one real screen with 2 or 3 open-licence pairings (Google Fonts, SIL OFL) next to the current look, ask the owner to choose, load them in the prototype, and record family, axes, weights and licence in `design-tokens.json` (`fonts`) and `DESIGN.md`. Re-run the verification: line lengths change.
2. **Prototype home.** Put the approved whole-app prototype at `docs/design/prototype/<name>.html` with its `assets/`, notes and tokens (the reviewer's whole-app check and `prototype_blessed_at` read this path, DR-056/DR-080). Keep earlier rounds in `mockups/` and fix their relative asset paths.
3. **Tokens from the final CSS.** Regenerate `design-tokens.json` mechanically from the prototype's CSS custom properties (light root and dark overrides), grouped (brand, colour, text-cover tints, type, space, radius, shadow, motion, layout, breakpoints), status `FROZEN <date>`. Move earlier proposals to `design-tokens-history.json`.
4. **Contract docs.** Replace the DRAFT banner in `DESIGN.md` with FROZEN and the approval date; mark `design-decisions.md` frozen with a freeze entry; freeze the AppShell contract in `components.md`.
5. **Per-feature shards.** Run `scripts/shard-prototype.mjs` with a config listing, per UI FRD, every screen AND every state its acceptance criteria name (loading, empty, error, partial coverage, dialogs, confirmations). Then write each `fdd.md` (template), citing the AC ids each screen realizes. Any FDD open question that a prototype state can answer is closed by adding that state to the shard config, not by leaving it open.
6. **Fidelity references.** Run `scripts/measure-components.mjs` with one entry per frozen component (shell, footer, headings, cards, tiles, covers, pills, buttons, toolbars, dialogs, skeletons, notices, story components) and an `exports` expression for the icon set and every logo variant. It writes `prototype/reference/computed-styles.json`, `prototype/components.html`, catalogue screenshots and the SVG files.
7. **Fidelity checklist.** Write `docs/design/fidelity-checklist.md` from `${CLAUDE_PLUGIN_ROOT}/templates/docs/fidelity-checklist-template.md`: the binding references table, the fonts, the product's signature details that are easy to lose (each with its selector), and how to verify a screen. Link it from `DESIGN.md` and every `fdd.md` (`## Fidelity references`).
8. **Requirements for Architecture.** Append to `docs/design/technical-assumptions.md`: self-host the chosen fonts; use the exported SVG icons and logo, never an icon-library substitute; automate a computed-style check against `computed-styles.json` in the end-of-build visual QA; load UI strings from the copy file verbatim.
9. **Gate.** Run `node "${CLAUDE_PLUGIN_ROOT}/skills/design/scripts/check-design-gate.mjs"` from the project root. Only `READY` plus the owner's approval writes the transition.

Also check `.pandacorp/status.yaml` on entry: if `phase` still says `product` while design work is happening, the product gate was approved but never recorded; confirm with the owner and set `phase: design`, so Mission Control and the gate read the truth.
