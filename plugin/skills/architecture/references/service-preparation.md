# Service and account preparation (DR-134)

Read `factory/standards/external-services.md` and `factory/services/catalog.yaml` from the factory path in `.pandacorp/guide.md`. Read the configured private registry (`<projectsRoot>/pandacorp-vault/services/accounts.yaml`) and this project's `.pandacorp/accounts/services.yaml`. Never dump secret values. Missing registry/access is pending, not permission to create a second account.

1. Before the decision round: inventory only needed providers and known existing project resources. Use exact resource_slug and default pandatrack.app subdomain. Preserve existing names/integrations. Reuse provider defaults; ask only genuine deviations/conflicts and explicit optional choices.
2. Resolve PostHog, Sentry, multilingual i18n, SEO and mailing-list need separately. Kit is off by default; ask whether subscribers belong in a mailing list. Silence is pending for explicit choices. No SDKs, stubs, keys, gates or WOs for deferred/excluded scope.
3. Select authorized account; verify identity/org and operation-specific API/CLI scope. Plan browser-only steps honestly. Persist native resource IDs and reconcile lookups before create/retry. No card, paid plan, new account, scope grant or external message without its applicable owner authorization.
4. Draft the value-free variable contract: name, purpose, current-version consumer path or owning WO, installed/planned consumer, origin, environment, exact app/worker/migration/local/CI destination, secret reference and status. This preflight inventories only; resource creation, provider credential retrieval/issuance and local secret generation wait until the decisions and contract are final. Admin tokens never enter app runtime. A web session proves neither CLI access nor a working recipe. Follow `environment-delivery.md` at step 9b3 to fill the approved values, not merely describe them.
5. Apply provider names/env policy: Neon project exact slug with dev/prod branches; real R2 <slug>-dev/prod, shared adapter locally/prod; Google shared PandaTrack project, one per-app client reused across callback environments; shared Resend domain and hello sender with app display/subject context; no routine staging. Detail and alternatives stay in catalog/standard.
6. Write approved selections and pending owner steps into architecture, FRD blueprints/work orders, project associations and owner digest, not copied personal identities in committed docs. Quotas/limits need official source and date plus live account evidence. Optional skips remain explicit. Use evidence dimensions independently; recipe documentation is not tested automation.
7. New service mid-build: return to minimal owner scope decision; record public recipe, private account and project association before adoption. Concentrated quota growth suggests isolating the dominant consumer; evenly shared growth needs policy-checked capacity options and owner approval, never fee-evading accounts for other providers; PostHog follows DR-160.

**PostHog provisioning (DR-160), only after an explicit now choice and finalized contract:** use the existing shared login from private account metadata. For a new app, create a new organization named after the app, choose US/EU at creation, and use exactly one project on the free plan without a card. On reruns, reconcile the app's stored organization/project before any create/retry. Record organization name/ID, project ID and region in the project `.pandacorp/accounts/services.yaml`; credentials follow the approved secret destinations, never reuse another app's key. If asked for a card, stop and escalate. Any PostHog notice/email/alert triggers owner reevaluation of the accepted Terms §2.1(d) risk and fallback in DR-160/catalog; do not activate a card/paid plan automatically. This exception authorizes no new login and no automatic migration.

Validation: `node <factory>/plugin/scripts/validate-service-catalog.mjs`. Catalog structure is deterministic; actual identity, budget, provisioning and runtime readiness require operation-specific evidence and are not certified by that command.
