# /pandacorp:architecture

Architecture phase. Runs IN the project (requires PRD, FRDs and frozen design). Produces **two artifacts**: the
technical blueprint (platform `docs/product/architecture.md` + one `blueprint.md` per FRD) and the work orders ready
to build, plus the installed stack and the owner's Spanish digest. The owner decides every owner-visible technical
choice in ONE round at the start (DR-131); everything else follows the standards.

> **Preflight (DR-045) — is this a Pandacorp project?** This skill mutates the project, so first confirm the Pandacorp marker: `.pandacorp/status.yaml` exists. If it's missing, STOP and tell the owner (in Spanish) that this folder isn't a factory project yet — `/pandacorp:adopt` brings an existing project in, `/pandacorp:spec` creates a new one. Then, if `overlay_version` in `.pandacorp/status.yaml` is behind the plugin's `OVERLAY_VERSION`, run `/pandacorp:upgrade` first (silent for compatible bumps, DR-048) so this skill runs against the current structure. Don't proceed or invent docs over a missing structure.

**References** (read the one a step names, when you reach it): `references/dispatch.md` (BEFORE the first
dispatch: tiers, parallel groups, inputs, budgets, context packs, speed rules, the Codex path),

unreadable): `build-packs.mjs`, `waves.mjs`, `ac-matrix.mjs`, `plan-consistency.mjs`, `flip-active.mjs [--dry-run]`,
`resolve-versions.mjs`.

## How the phase runs (read once)

- **Owner pacing (Pareto).** At the start, tell the owner in Spanish the plan in five lines with its wall-clock and
  token budget (`references/dispatch.md` §3: about ≤ 5 h and ≤ 6 M subagent tokens for 6 to 8 FRDs averaging ~12
  ACs, scaled).
  Then milestone messages only: (1) the decision round, (2) plan ready, (3) gates passed, (4) merged + digest. Before
  any step expected to take more than 30 minutes that the plan did not announce (a design mini-round, a spike, a
  second gate run), state the estimate and the cheaper alternative first. No audits beyond the three gates; owner
  visual reviews never block; one fix pass.
- **Agent reality.** `architect`, `product-manager`, `copywriter` and `researcher` have no Bash: the LEAD runs every
  mechanical check (JSON parse, doc-lint, residual-ambiguity, the scripts above, `check-fdd-coverage.mjs`) and every
  `git rm` (a Bash-less agent tombstones a file as `# OBSOLETE: <path> (reason)`; the lead deletes it before the next
  check). An agent cut by a rate limit is resumed with `SendMessage` to the same agent, never restarted.
- **Isolation (DR-096).** Reading and the decision round happen in the main checkout. The first write under `docs/`
  happens in a worktree: `EnterWorktree`, then `bash .pandacorp/worktree-bootstrap.sh`. When the repo has no
  `origin/<default>` ref (never fetched / no remote), create it by hand from local HEAD
  (`git worktree add -b <branch> .claude/worktrees/architecture HEAD`), run the bootstrap there and work in it by absolute path. Gitignored files
  (`.pandacorp/comms/`, `.pandacorp/run/`) do not travel with the merge: owner-facing comms are always written to the
  MAIN checkout's path.
- **Dispatch: speed, parallelism, portable tiers (`references/dispatch.md`).** Every agent runs at the `TIER·effort`
  its row gives (MECH / STANDARD / JUDGE, PORT-2), resolved at dispatch time from
  `${CLAUDE_PLUGIN_ROOT}/runtime/model-tiers.json` (Claude: the tier alias as the `Agent` `model` plus `effort`,
  overriding a named agent's pinned default; Codex: the tier worker, read-only on build state per DR-120;
  elsewhere: inline, sequential). No model name
  is written in this skill or its briefs. Each group (G1 to G5) is launched in ONE dispatch message, in the
  background. Agents read context packs (`build-packs.mjs`) plus the `frd.md` files they plan or judge in full, not
  the doc set; the lead reads reports and script
  outputs, not the docs. A stage past 2× its budget stops and the owner gets the cheaper option. A late change is a
  scoped delta, never a regeneration.

## Steps

0b. **Input readiness preflight — STOP early, never discover a design gap mid-phase.** From the project root, with
   the CURRENT plugin: `node "${CLAUDE_PLUGIN_ROOT}/skills/design/scripts/check-design-gate.mjs"` and
   `node "${CLAUDE_PLUGIN_ROOT}/skills/design/scripts/check-fdd-coverage.mjs"` (DR-130), and confirm the PRD/FRDs are
   ACTIVE. A headless project (root `DESIGN.md` states "no UI — design phase N/A") skips the design checks. If either
   check is not clean: STOP before any architecture work and tell the owner in Spanish the counts (failing checks,
   pictureless FDD states per FRD) and a time estimate for the fix (funko-tracker: 130 states drawn in 5 batches took
   about 11 h with API limits, so budget roughly 5 minutes per missing state plus re-capture), with the cheaper
   alternative (the owner takes that UI out of the FRD). Route the fix to a design mini-round through
   `/pandacorp:design` (its DR-130 path, `skills/design/references/freeze-and-fidelity.md`), then re-run this step.

1. **Decision round — the owner decides before any document (DR-131, owner gate; replaces the old one-shot stack
   approval, DR-002).** Follow `references/decision-round.md`. The `architect` (with the `researcher` for web facts;
   the lead runs `curl`/registry checks) drafts a Spanish decision brief at `.pandacorp/comms/arquitectura-decisiones.md`:
   every owner-relevant decision with its context (citing the FRD/AC), 2–3 alternatives with trade-offs (cost/month,
   risk incl. legal, effort, the owner's ops workflow), the recommendation and why, verified facts (tested live, dated,
   never from memory) and the cost of changing it later. **Mandatory triggers** whenever the product has one: stack
   and any golden-path deviation (starting from `factory/standards/stack.md`, latest stable versions); hosting and the
   monthly cost envelope; **media and third-party content (store vs hotlink vs same-origin proxy, sources, rights
   stance)**; **data ingestion/curation (in-app pipeline vs owner-run agent skills vs manual) and whether an
   admin/operator web UI is needed at all**; external data access and legal; background compute and AI cost; auth and
   deletion promises; email/notifications; backups/retention; and prior art from sibling
   factory projects ("en <proyecto> lo resolvimos así"). Ask them in ONE round with `AskUserQuestion` (at most 4 per
   call, recommended option first; other runtimes ask in chat); lock every answer as an ADR + a decision-log entry.
   **Always resolve four separate choices, even for an internal or single-language app:** PostHog analytics;
   Sentry error tracking; internationalization scope; and SEO now, including metadata. Use the explicit options and
   boundaries in `references/decision-round.md` §2. Reuse verified, explicitly settled project decisions on reruns;
   otherwise ask. These four require an explicit answer (including "como recomiendes"): silence/skipping is NOT
   approval, and the round remains pending before downstream work. Other unanswered questions take their
   recommendation, recorded as default. Purely technical choices with no owner-visible trade-off follow the
   standards silently; durable conventions (`factory/standards/`) are not up for debate.

   **Scope contract for every downstream step, agent, context pack and template:** carry the four locked outcomes
   from their ADRs into the platform architecture, FRDs, per-FRD blueprints and WOs (including dependencies),
   package installs, env/secrets, validation and build-hardening/release close-out requirements. A default stack,
   dispatch row or template cannot opt a capability back in. Deferred/excluded scope has no SDKs, wrappers/stubs,
   required secrets, instrumentation/SEO tests or provider-specific account-erasure tasks; retain only the decision
   and revisit condition. Preserve independent auth/account erasure and the baseline centralized translatable UI
   strings. Reconcile existing conflicting requirements before planning; if an installed scaffold or canonical gate
   forces excluded scope, surface the conflict and stop rather than enable it or edit a verbatim gate.

   **MVP/v1 database recovery:** use only the DB provider's native recovery, after verifying the chosen plan's
   actual availability and recovery/retention window (`references/decision-round.md` §2). Never plan or install
   own DB backups to R2/S3 or another external store in MVP/v1: no dump jobs, backup buckets/keys, custom restore
   machinery or speculative tests/secrets. Carry this boundary through architecture, blueprints, WOs and their
   dependencies, installs/env, validation and close-out; evaluate external backups only after product validation.
   A legal/FRD guarantee the provider cannot meet blocks planning for an owner-visible resolution, not an implicit
   backup system or a silently weakened promise. Product exports/media storage are separate legitimate scope.
   This prospective rule does not authorize removing any existing implementation, including this project's.

2. **Architecture — two layers, never fused (DR-049)** (`architect` agent, from the locked decisions):
   - **Platform architecture** (`docs/product/architecture.md`, stable, ONE per project, following `${CLAUDE_PLUGIN_ROOT}/templates/docs/architecture-template.md`): approved stack, high-level architecture, complete data model, **media & third-party content**, **operations & admin tooling**, deploy strategy, cross-cutting concerns and service boundaries — the things that are stable across features.
   - **Per-FRD blueprint** (`docs/frds/frd-NN-<slug>/blueprint.md`, one per FRD in scope; written in step 9 through the planning pipeline): how THIS feature is implemented on top of the platform — its components `CMP-NN-<slug>` and interfaces `IF-NN-<slug>`, API/action contracts and external integrations specific to the feature (limits and costs), each traced back to the FRD's `REQ-NN-MMM`. Each blueprint follows `${CLAUDE_PLUGIN_ROOT}/templates/docs/blueprint-template.md`: it restates the **source-of-truth hierarchy** in its header, references `docs/product/architecture.md` instead of re-describing the platform, carries the **state frontmatter** (`status` + `implementation_status`), and MUST include a **Build Plan** — the DAG of that FRD's work orders as the mandatory table (which is first, which depend on which, what runs in parallel, the integration order, and any cross-FRD dependencies). **The build engine READS this Build Plan instead of re-inferring dependencies at runtime (DR-050).** The Build Plan also **records each WO's `artifacts` (the globs of files/dirs it writes) and must be verifiably DISJOINT within a wave (DR-060)**: the engine serializes any overlap into a later wave, but the plan should be disjoint by design. The API contract is **per-WO at `docs/api/<wo-id>.md`** (in that backend WO's artifacts), never a single shared file.
     - **Foundation wave first (DR-057).** Before the feature work orders fan out, the Build Plan MUST identify the **shared design-system foundation** — the core primitives that multiple features reuse (`Button`, `Banner`/`Alert`, `Card`, `Chip`, `Modal`, `Input`, `Table`, …) — and schedule them as the **FIRST work order(s)**, a *foundation wave* that completes BEFORE any feature work order starts. That wave produces the primitives in `components/core`/`components/modules` **and seeds the living component inventory `docs/design/components.md`** (name · purpose · path · key props/variants). Feature work orders declare a **`Dependency` on the foundation WO** and build against real, existing primitives — never reinvent them (parallel feature agents never talk to each other).
       - **The persistent APP SHELL is a foundation work order too (DR-075):** when `design` Step 8a captured an `AppShell`/`Nav` in `components.md`, schedule it in the foundation wave — its `artifacts` include `app/layout.tsx` + the nav component — so every surface route mounts into it. A foundation WO, **not** a new FRD, so the foundation-completeness gate enforces "no surface until the shell is green" with no `REQ-NN-MMM` spine collision.
       - **Foundation-WO NUMBERING (do NOT invent a `00` FRD):** foundation/shell work orders belong to a REAL owning FRD — almost always the platform-shell feature **FRD-01** — numbered as its own correlatives (`WO-01-001`, `WO-01-002`, …) with `parent: FRD-01` + `foundation: true`. The "Wave-0 foundation" fact lives in **`foundation: true` + the Build Plan/`dependsOn`**, NEVER in a `WO-00-*` prefix (a `00` id is a defect the readiness gate rejects).
       - Large feature → promote `blueprint.md` to a `blueprints/` folder split by coherent concern (`blueprint.md` keeps the frontmatter and the Build Plan). A single global `docs/blueprint.md` is an anti-pattern.
   - ADRs in `docs/adr/` (each following `${CLAUDE_PLUGIN_ROOT}/templates/docs/adr-template.md`): one per locked owner decision (step 1) and one per other non-obvious platform-level decision. **For monetary/mixed (DR-042)**: compute the **per-active-user variable cost** (Polar fee ~4%+$0.40, Vercel Pro share, Neon/R2/Resend/PostHog usage tiers) and hand it to the PRD's unit-economics block so the break-even is real, not a guess.
2b. **Publish the logical model (DATA-7, every stack).** Write `docs/product/data-model.json` from the approved platform model using `${CLAUDE_PLUGIN_ROOT}/templates/rules/logical-data-model.md`'s version-1 contract (also injected into `docs/rules/`). Include every entity/attribute, type, optionality, PK/FK/UQ/composite group, explicit mapping and both endpoint cardinalities. No database means explicit `persistence: none` and empty arrays, never omission or a guessed schema. Link the artifact and canonical source/exporter from architecture.md. Regenerate on every model revision; the fresh architecture readiness verifier compares the source and artifact before approval. Model-changing work orders MUST own this artifact and its reviewed update in their declared scope; order shared-schema/model writers serially under existing overlap rules, rather than giving parallel WOs an undeclared shared write. During implementation and later changes, follow DATA-7's same-change/commit freshness rule; no build-state transition is introduced. (The lead parses the JSON; the `architect` cannot.)
3. **Event plan — only when PostHog is explicitly chosen for now** (`analytics` agent; otherwise skip this
   dispatch and the event catalog): translates the PRD's success metrics and value hypothesis into `docs/analytics/events.md` (following `${CLAUDE_PLUGIN_ROOT}/templates/docs/events-template.md`; which event measures each metric, where it fires, what properties — no PII, DR-025). Only the chosen scope is instrumented in `implement` and verified by the build's hardening step (DR-085 — the engine's telemetry-verification stage; `release` only confirms it live).
   When analytics is deferred/excluded, the lead writes only a short scope record in `docs/analytics/events.md`: the decision ADR, no planned events, measurement limitation, revisit condition and `## Verification` stating telemetry is not applicable to this version. This documents scope for the existing hardening evidence contract; it is not an event plan, SDK stub or provider-verification task. Never populate the event template with speculative future events.
4. **Deploy design** (`devops` agent, only if the project actually deploys): deployment section/ADR — where to, environments (dev → staging → prod), reproducible CI/CD pipeline, secrets management (SOPS+age store, `factory/standards/external-services.md`) and rollback plan, starting from `factory/standards/infra.md`. **If v1 includes payments (PRD, DR-035) and the host is Vercel, WARN the owner** (warning, not a blocker): charging requires Vercel Pro (Hobby is non-commercial, full account ban) → it triggers a push (DR-038) and the owner decides (ideally already in step 1's hosting decision). For a trivial project with no deploy of its own, the standard is enough and this step is skipped.
5. **Cross-validation + feasibility + FRD reconciliation**: each FRD must be implementable on the platform (its REQs land on platform modules; the per-FRD `CMP-NN-<slug>` mapping is then asserted by step 9's readiness gate). **Read `docs/design/technical-assumptions.md`** (the designer's feasibility flags): for each costly/risky assumption (real-time, offline, server-side media, costly/uncertain third-party, scraping with ToS/rate-limit risk) confirm the architecture can support it cheaply; if a critical technical unknown remains, run a **timeboxed feasibility spike to prove it BEFORE committing the data model and work orders** (don't discover infeasibility mid-build; announce the spike's estimate if it exceeds 30 minutes). **If the cross-validation, a spike or a locked decision changes an FRD's criteria, the `product-manager` updates the affected FRD(s) (+ADR) before work orders are generated** — work orders must never carry stale criteria (anti spec-drift). If something doesn't add up, go back to the `architect` before continuing.
6. **Install the stack** — follow `references/stack-install.md` (a STANDARD-tier installer with Bash; the lead checks byte identity). **Byte-identical-copy rule (DR-059)**: every canonical file (gate config, `verify.sh`/`canary.sh`, the e2e set) is copied byte-for-byte from `${CLAUDE_PLUGIN_ROOT}/templates/stack-<chosen>/`, never hand-rolled; project additions go in separate files. Sub-steps, all binding:
   - **(a) Provisional-stack harness gate (BL-0016, DR-105) BEFORE any VERBATIM copy**: if `templates/stack-<chosen>/verify.sh` is absent (stacks B/C, and D which resolves to C), build that one stack's canonical harness first and prove it with `verify.sh --canary`, or STOP and escalate; never an ad-hoc gate.
   - **(b)** canonical gate config VERBATIM (`biome.json`, `knip.json` → root; `verify.sh`, `canary.sh` → `.pandacorp/`).
   - **(c)** the e2e gate machinery VERBATIM + seed-only `e2e/{routes,_target,shell}.ts` (the DR-075 nav contract from design Step 8a) + the `test:smoke|visual|responsive|shell` scripts + `@axe-core/playwright`.
   - **(d)** dev ports from `dev_port_base` into `.claude/launch.json` and `.env` (DR-022).
   - **(e)** exact versions at the install point (DR-102, SEC-4 cooldown) with `resolve-versions.mjs`: stable only (never a prerelease, even under the `latest` tag), at least 7 days old, peer and family majors aligned; the table is recorded in `architecture.md` "Pinned versions"; `pnpm add --save-exact` now or the exact command in the WO that installs it. `server-only` only if a WO installs it and no worker/CLI imports those modules.
   - **(f)** `.env.example` (every env var), `AGENTS.md` pointing at the framework's version-matched docs, and the README "Getting started" read from what was just installed (DR-112/DOC-3).
6b. **Inject the tech-gated engineering rules** from `${CLAUDE_PLUGIN_ROOT}/templates/rules/` (every file whose `applies_when`/`also_applies_when` matches a technology this project uses; verbatim, never re-condensed) into `docs/rules/` and regenerate `docs/rules/README.md` (canonical spec in the `scaffold` skill). **Then cross-check them against the frozen design contract** (`technical-assumptions.md`, `fidelity-checklist.md`, `DESIGN.md`): every conflict (e.g. `web-performance.md`'s `next/image`/`next/font` vs a pixel-exact fidelity contract) becomes a project exception in an ADR + one line in `architecture.md`; the copied rule file is never edited.
7. **`.pandacorp/verify.sh`** (used by the Stop hook): this is the canonical `verify.sh` installed VERBATIM in step 6 (DR-059) — do NOT author a fresh one. It is MAXIMUM fail-closed (DR-019): `set -euo pipefail` + `inherit_errexit`, every Biome warn promoted to a hard gate (`--error-on-warnings`), `tsc`/`knip`/`madge`/`vitest`, and the smoke (DR-055) + visual (DR-056) + responsive (DR-074) + shell (DR-075) shims where a **missing** harness is RED, never a skip — with actionable messages. Confirm it runs; never hand-edit it (drift fails the conformance check).
8. **CI**: GitHub Actions with lint + typecheck + tests on PR (template in the stack guide). Toward main: **mutation testing** (Stryker/mutmut, DR-016) + **OWASP agentic audit** if applicable (DR-017) + **changelog/ADR** generation (DR-018). Branch protection on main if the GitHub repo exists. The deploy pipeline was left designed by the `devops` (step 4). Plan the CI services the tests need (e.g. a Postgres service once DB tests land) in the WO that adds those tests.
   - **Visual spec for UI features (DR-054).** For a UI FRD (`ui: true`), the Build Plan must point implementers at the FRD's `fdd.md` + the specific `mocks/` screen(s) as the **binding visual spec to reproduce** (layout, structure, components, density — not an approximation; "uses tokens" is not enough), and **enumerate the assets the screens need** (fonts/images/sprites/icons) so they get staged (e.g. into `public/`) and actually render. The fidelity is checked by the preview smoke gate (DR-055) and the blocking fidelity gate (DR-129).
9. **Work orders + blueprints through the planning pipeline** (`references/planning-pipeline.md`, executed per `references/dispatch.md` G2 to G4, every agent on its context pack): ONE planner writes the cross-FRD work-order map (`references/wo-map-template.md`: foundation wave, every AC → exactly one WO, artifacts, dependsOn, waves, one owner per shared file per wave, exact install commands, binding resolutions); parallel `architect` authors per FRD group write blueprints + work orders from the map with `references/blueprint-author-brief.md`; each writes its cross-FRD requests to its own ledger file, concatenated by the lead; ONE reconciler applies it across all FRDs; the lead runs the scripts. Work orders are **coarse per-FRD** (see the `work-orders` skill) following `${CLAUDE_PLUGIN_ROOT}/templates/docs/work-order-template.md`, born **`status: DRAFT`** (they flip to `ACTIVE` only in step 9b2, nothing is born `ACTIVE`). Each is **one cohesive view / page / capability** (NOT an atomic component), carries the **state frontmatter** (`implementation_status: PLANNED`; `artifacts: [globs]`, DR-060; **`difficulty: low | medium | high`** — `high` builds on the JUDGE tier a-priori, DR-073; without it the escalation silently never fires), a filled `## Summary` (BL-0015) and a `## Status Note` hand-off, cites its `REQ-NN-MMM`/`AC-NN-MMM.K`/`CMP-NN-*`/`IF-NN-*` with each owned AC **copied verbatim** as its `- **AC-…**` bullet, and lists `dependsOn` consistent with the Build Plan. A UI work order carries its filled `## Visual reference` (DR-054). **TEST-SIDE SUPERSESSION (BL-0051)** — when a work order DEROGATES a contract an existing blessed reviewer test asserts: the re-bless MUST NOT sit behind a `dependsOn` edge on the derogating WO; either (a) fold derogation and re-bless into the SAME WO, or (b) put the re-bless in a WO that does not `dependsOn` the derogating one, so the FRD gate sees both in the same wave (LESSON-0104; DR-116's test-side analogue). Per-FRD list in `docs/frds/frd-NN-<slug>/work-orders/README.md`. A content-heavy product's plan states that fixtures exercise the app and the real content is a separate later track (BL-0244). Then the **READINESS GATE (DR-100)** by a FRESH agent, never the author — this gate, 9b's repo-grounding validation and 9b-consistency's contradiction gate are **three independent fresh-agent gates that run IN PARALLEL, each in its own context (constitution §24)**, tiered by `references/dispatch.md` G5 (grounding and consistency JUDGE·medium; readiness = the lead's scripts + one STANDARD·medium check) (`references/gates.md`). The lead runs the mechanical pre-checks first (`waves.mjs`, `ac-matrix.mjs`, `plan-consistency.mjs`, `check-fdd-coverage.mjs --plan`, data-model JSON parse, doc-lint, residual-ambiguity) and fixes a red script before spawning them. The readiness gate asserts fail-closed: every `REQ` maps to a component, **every `AC` is covered by exactly one WO**, the data model has no `TBD`, `dependsOn` is acyclic + complete, wave artifacts are disjoint and complete, the foundation is complete, **no `[NEEDS CLARIFICATION]` survives**, **each backend WO's API contract has an owner** (a WO whose build step materializes `docs/api/<wo-id>.md` before its consumer runs, DR-060), and **every UI FRD plans only UI its frozen oracle captures (DR-130)**: `check-fdd-coverage.mjs --plan` exits 0. A red caused by the FDD or the prototype is a DESIGN defect: stop and route it back to `/pandacorp:design`; never plan around it, never edit the prototype or the oracle from here.
9b. **REPO-GROUNDING VALIDATION (DR-102)** *(in parallel with 9 and 9b-consistency, its own context, JUDGE·medium)*: every concrete claim in `architecture.md` + the blueprints + the work orders checked against the scaffold installed in step 6 — cited paths exist or are creatable under the installed framework's conventions; framework APIs/config keys are current for the INSTALLED major (the version-matched docs, not memory); every dependency version is installed or carried as an exact `pnpm add` in a WO, none a prerelease; hard guarantees (rendering/SSG) are achievable (a real `pnpm build` where it matters); modules meant for a worker/CLI import nothing framework-only. Any mismatch is a BLOCKER fixed before `ACTIVE`. Altitude (DR-100): grounded and current, not voluminous.
9b-consistency. **FRESH-SET CONTRADICTION GATE (DR-116)** *(in parallel with 9 and 9b, its own context, JUDGE·medium)*: no hard contradiction survives across `architecture.md`, the blueprints and the work orders (a WO vs its FRD/blueprint, a blueprint vs architecture.md/the PRD, two blueprints giving one artifact incompatible shapes, one term meaning two things, a doc vs a locked-decision ADR). Any hard contradiction is a BLOCKER; the docs STAY `DRAFT`. Canonical: `factory/standards/document-consistency.md`.
   **Then ONE fix pass** over the blockers of all three reports, the lead's deterministic re-verification (every pre-check + one targeted grep per blocker) and a `## Resolution addendum` ending "Verdict after resolution: PASS" appended to each FAIL report. A second full gate run only when a fix changed scope; later iterations and mid-phase owner changes get a **delta review** scoped to `git diff` (`references/gates.md` §5).
9b2. **The DRAFT→ACTIVE flip — owned HERE, with the evidence stamp (audit-20 P1-3/P1-1):** `node "${CLAUDE_PLUGIN_ROOT}/skills/architecture/scripts/flip-active.mjs" --dry-run`, then without `--dry-run`. It refuses unless ALL THREE gate reports end PASS (or with the PASS resolution addendum) and the plan scripts are green; then it sets each blueprint's `status: ACTIVE` **and stamps** `readiness_gate: passed YYYY-MM-DD`, `grounding_gate: passed YYYY-MM-DD`, `consistency_gate: passed YYYY-MM-DD` in the same frontmatter, and flips that FRD's work orders `DRAFT → ACTIVE`. The stamp is what makes the gates CHECKABLE downstream: `/pandacorp:implement`'s preflight REFUSES an ACTIVE blueprint without these fields, and `verify.sh`'s DR-100 marker scan covers the rest. Never flip on a partial pass, never flip to silence a gate. (The PRD/FRDs' own ACTIVE flip belongs to `spec`, at the owner's "ok, advance".)
9c. **Architecture digest — the owner-facing Spanish summary (powers Mission Control's "Arquitectura" tab).** Write `.pandacorp/comms/arquitectura-resumen.md` **in the MAIN checkout** (gitignored files do not travel with the merge) following `${CLAUDE_PLUGIN_ROOT}/templates/docs/architecture-digest-template.md` — a HIGH-LEVEL, scannable **Spanish** digest of the platform architecture: the stack table (capa · elección · por qué from `docs/product/architecture.md`), the **data model** (the DB schema/entities when the project has one; for a content-as-code / no-DB project a one-line "Sin base de datos — contenido como código" + the content entities), communication & services, and ONE card per FRD (its blueprint one-liner + its work orders summarized). Mission Control renders it natively in the **Arquitectura tab** (after Spec), available when this digest or the structured model exists; Portfolio reuses the complete Architecture view after Work orders. The logical diagram/Esquema reads `docs/product/data-model.json` (DATA-7), not narrative bullets; keep the **Modelo de datos** heading and narrative aligned without maintaining another schema. The implementation-plan DAG, the ADRs and the env vars are read LIVE by the tab from the real artifacts (the work-order frontmatter, `docs/adr/*`, `.env.example`) — the digest does NOT duplicate them. It is a SUMMARY for the owner, **not a copy** of the docs. **Keep the template's markers EXACTLY** (the `## 🧱 Stack & tecnologías` table, the conditional `## 🗄️ Modelo de datos`, `## 🔌 Comunicación & servicios`, and the per-FRD `### FRD-NN · Título` + `**Blueprint:**` / `**Work orders:**` blocks) so the tab's parser renders it rich. **Include the four decisions (now/deferred/excluded, with the i18n scope) and their revisit conditions in the existing summary blocks.** After the digest is complete, the lead compares its four scope choices with the locked ADRs; fix a mismatch before landing. **Regenerate it on every `architecture` iteration** so it never drifts from `architecture.md`/the blueprints.

10. **Land, then the iterate / advance gate (DR-032).**
   - **Land:** commit in the worktree (Conventional Commits, only your files), then `bash .pandacorp/merge-queue.sh`. If it hands back (conflict, red gate, busy main), tell the owner at once what is blocked, why, and that the work is preserved on its branch (DR-099). After it lands: `pnpm install --frozen-lockfile` in the MAIN checkout (so `verify.sh` and the Stop hook find the tooling there), then, when the repo has a remote, `git push origin <default>` (the owner wants GitHub in sync; private repo, DR-010; never force), then `ExitWorktree(action: remove)`. Tell the owner "merged" with the digest (milestone 4).
   - **Advance gate:** if a blueprint/work orders already existed, this is an **iteration** — read `.pandacorp/comms/iteration.md` (phase `architecture`) and refine what's there (don't regenerate or repeat what was discarded), appending one entry per round; a changed decision gets a delta review, not a regeneration. Present to the owner: the locked decisions, the stack and why, estimated cost, risks, and how many work orders/waves. **Don't start the build on your own:** leave `advance_pending: true` in `.pandacorp/status.yaml` and **wait for their "ok, let's build"** — re-running `architecture` in the meantime = keep polishing the plan. When they approve: `.pandacorp/status.yaml` → `phase: architecture` (ready to build) + `advance_pending: false`, and close the `architecture` thread in `.pandacorp/comms/iteration.md`. Next step: `/pandacorp:implement`.

## Rules
- The TECHNICAL research happens HERE (stack, libraries, integrations, limits): leave little to resolve during the build. The dev agents only research specific gaps on demand.
- The MINIMUM that satisfies the FRDs: no microservices, no speculative infrastructure features, ~$0 cost at launch.
- If an external integration requires payment (paid API, plan), DR-005 applies: escalate to the owner with the amount (in the decision round when it is known then).
- An owner-visible choice is never made silently (DR-131): it is in the decision round, or it waits for the owner.
- A tool defect found during the phase (a check script, the merge queue, the bootstrap) is fixed in the factory (a `BL-*` item), never by a project-local replacement; capture the lesson in `.pandacorp/run/lessons.md` in the same turn.
