# /pandacorp:implement

**This is the command that starts (and resumes) the build. The active runtime selects its own executor; runtimes never call one another.** Under Claude Code it launches the **dynamic workflow** `pandacorp-build`, a native Claude Code JS script that runs in the background and builds in **GLOBAL WAVES** (DR-050 + BL-0021). **No other runtime has a build executor: every non-Claude runtime is read/review-only on build state (DR-120 freeze, 2026-09-02).** The executor reads each blueprint's Build Plan and the work-order frontmatter **`implementation_status`** as canonical state, and requires an independent review/test gate before an FRD becomes `VERIFIED`.

## Runtime selection — do this before interpreting the rest of the skill

- **Claude Code:** keep the existing path unchanged. Use `pandacorp-build` + the Claude supervisor, Claude agents/models and the Unattended operation SOP below. Its normal bare/global, targeted and unattended capabilities remain available.
- **Codex — STOP.** Read the canonical capability policy (`plugin/runtime/skill-runtime-policy.json`): `implement.codex.status` is `FALLBACK`, read/review-only. **Do not launch anything.** Do not invoke `plugin/scripts/launch-codex-implement.sh`, `plugin/runtime/codex/executor.mjs` or its supervisor. You may read the Build Plan, the work orders and `status.yaml`, review them and report to the owner in Spanish — that is the whole permitted surface. The former `EXPERIMENTAL/attended_foreground/targeted-only` profile was withdrawn on 2026-09-02 (DR-120, reopen trigger: *"Codex ships wake-capable local scheduling"*).
- **Any other runtime (Cursor, OpenCode, …): STOP** — same read/review-only boundary. No build-state writes are authorized from any non-Claude runtime.

The remainder of this file describes the Claude build contract — **the only executable one today**. Governance it states (frontmatter states, leases, independent review, `verify.sh`, mutation evidence, safe points and human gates) binds every runtime as instructions even where the mechanism is Claude-only.

> **Preflight (DR-045) — is this a Pandacorp project?** This skill mutates the project, so first confirm the marker `.pandacorp/status.yaml` exists. If it's missing, STOP and tell the owner (in Spanish) that this folder isn't a factory project yet — `/pandacorp:adopt` brings an existing one in, `/pandacorp:spec` creates a new one. Then, if `overlay_version` is behind the plugin's `OVERLAY_VERSION`, run `/pandacorp:upgrade` first (DR-048) so the project's `.claude/engines/pandacorp-build.js` and structure are current. Don't proceed over a missing/stale structure.
>
> **Readiness re-check (DR-100/DR-102) — the gates' evidence, asserted for real (audit-20 P1-1).** Before launching, verify the plan actually passed its gates — this used to be a claim four docs made with no mechanism behind it; now it IS the mechanism: (a) every per-FRD `blueprint.md` with `status: ACTIVE` carries the **`readiness_gate: passed …`, `grounding_gate: passed …` and `consistency_gate: passed …` stamps** (written by `architecture` step 9b2 when its fresh-agent gates passed — an ACTIVE blueprint without them never passed the gates: STOP and route back to `/pandacorp:architecture`); (b) `grep -rn "NEEDS CLARIFICATION" docs/` finds no marker in an ACTIVE doc (the DR-100 blocker — `verify.sh` also REDs on it, this is the cheap pre-launch echo); (c) work orders to build have `status: ACTIVE` (a DRAFT WO is un-gated — don't build it). A legacy project whose ACTIVE blueprints predate the stamps: warn the owner once and offer to run the gates retroactively via `/pandacorp:architecture` — don't silently build.
>
> **Concurrent-run guard (DR-050 §11) — only one build per project at a time.** `preflight-implement.sh` (Launch checklist step 1) mechanizes this; the rule it applies, crossing the PRODUCER's own clock (DR-066) — after confirming `status.yaml` exists, read `running`, `run_started_at`, `supervisor_heartbeat` AND `last_event_at`:
> - `running: false` (or field absent) → proceed.
> - `running: true` AND **EITHER `supervisor_heartbeat` OR `last_event_at` is less than 10 minutes old** → **ABORT**. Tell the owner in Spanish that there is already an active build (include `run_started_at` so they know when it started). Do NOT launch the workflow. (Crossing `last_event_at` in is what stops a build with a quiet supervisor but a live engine from being misread as dead.)
> - `running: true` AND **BOTH `supervisor_heartbeat` AND `last_event_at` are 10 minutes old or older** (or both absent) → **stale lock**: the supervisor died (internet cut, crash, etc.). Warn the owner, reset `running: false` and clear `supervisor_heartbeat` in `status.yaml`, then proceed normally — the frontmatter state is still valid and the engine resumes without re-doing `VERIFIED` work.

`$ARGUMENTS` optional:
- **mode** (`pro` | `balanced` | `powerful` | `deep`; default `powerful`) — controls concurrency and model quality.
- **`frds`** — one or more FRD identifiers to target. The workflow normalizes the input automatically, so all these formats are valid: `'frd-05-settings'` (folder name), `'docs/frds/frd-05-settings'` (relative path), `'docs/frds/frd-05-settings/frd.md'` (path to file). When set, the engine builds **only those FRDs** and skips everything else. If any requested FRD has cross-FRD deps that are not yet `VERIFIED`, the build **refuses to start** and tells you which deps to implement first. **Mutually exclusive with `change`** — if `change` is set, `frds` is derived from it automatically. The launcher-printed `Workflow()` call carries this field plus `projectDir`, `project`, `leaseToken` and `leaseEpoch`; never hand-construct the call.
- **`change`** — a change from `.pandacorp/inbox/changes/` to process and build in one targeted run. All these formats are valid and normalized automatically: `'mc-observability-consumer-dr066'` (slug), `'mc-observability-consumer-dr066.md'` (with extension), `'.pandacorp/inbox/changes/mc-observability-consumer-dr066.md'` (full relative path). The engine: (1) opens the file exactly (no fuzzy search — if it doesn't exist it lists available ones), (2) verifies `status: ready` (the queue enum is `draft | ready | building | done`, DR-069 — a `draft` is skipped; an owner decision is NOT a queue status, it routes through `.pandacorp/inbox/decisions.md`), (3) creates/updates FRDs + WOs via the iterate/bug engine inline, (4) sets `ONLY` = the affected FRDs, then (5) runs the normal plan + dep-check + build loop for those FRDs. Wins over `frds` if both are passed. The launcher-printed `Workflow()` call carries this field plus the fenced lease receipt; never hand-construct it.
- `maxFrds` (**opt-in** cap on features **processed** per run — built + blocked + **reopened**, so reopens count — for **supervised TEST runs**).
- **`maxAgents`** (a hard cap on subagents spawned this run — **the real guardrail for overnight runs**: counted inside the engine, it brakes reliably even if `budget.spent()` under-counts subagent work or the supervisor dies; an integer, or the opt-in literal `auto` where the engine sizes the cap from its post-plan projection — see the Budget row below).
- `maxSpend` (an output-token ceiling via `budget.spent()` — a **secondary** ceiling, since it under-counts the heavy subagent work).

**Targeted build (partial implementation) — when the owner asks to implement only one FRD or a subset:** parse the FRD name(s) from `$ARGUMENTS` (accept both the short slug like `frd-05-settings` and a plain name like `settings` — resolve to the full folder name by scanning `docs/frds/`), pass them as `args.frds`, and follow the usual launch + supervisor flow. If the dep gate fires (unsatisfied deps), **stop immediately** before launching the workflow and tell the owner in Spanish which FRDs must be implemented first — do not launch. A targeted build still runs the complete per-FRD review/test gate; it does NOT skip review or tests. The whole FRD is the oracle: requirements, numbered acceptance criteria, invariants, edge cases, limits, errors and exclusions are inventoried in the verdict; numbered AC success never waives another normative clause, and every applicable edge/limit class gets an adversarial boundary test. It then quiesces as a partial run and keeps `phase: implementation`: project-wide DR-085 hardening, cross-feature close-out and `phase: release` belong only to a later bare `/pandacorp:implement` with no `frds`/`change` target.

**Targeted change build — when the owner asks to implement a specific pending change from the queue:** parse the change name from `$ARGUMENTS` (the filename without `.md` or a recognizable substring) and pass it as `args.change`. The workflow processes the change FIRST (creating/updating FRDs+WOs), then builds the resulting FRDs. If the change is `draft` (the only pre-`ready` queue status, DR-069), the engine stops immediately and tells the owner to flip it to `ready` first. If the resulting FRDs have unsatisfied deps, the dep gate fires as usual.

> **Non-Claude runtimes do not run targeted builds either.** A targeted change build is still a build-state write, so it is denied everywhere outside Claude Code (DR-120).

> **Engine = Dynamic Workflows, not Agent Teams** (DR-013). The per-FRD loop lives in the **script's code**, not in messages between peer agents. **Resumable by construction**: state lives in the work-order frontmatter + commits, so a re-launch reads `implementation_status` and **never rebuilds a `VERIFIED` work order** (DR-050) — no re-work.
> This is the **Claude-local executor**, and since DR-120 the only one. It dispatches only Claude agents
> and never invokes, messages or delegates to another runtime. The Codex executor
> (`runtime/codex/executor.mjs`) is frozen: it may not be invoked, and no cross-runtime continuation is
> authorized while the freeze holds (PORT-5).

## Execution modes (consumption/quality control)

Control the **concurrency and models** of the workflow (DR-014), not "team size":
- **pro**: minimum consumption. Up to 2 work orders at a time, economical worker (sonnet). A single full-stack `implementer` (no split). The `reviewer` still gates each FRD **on opus** — the judge is ALWAYS a different model from the worker (DR-015): pro economizes on throughput, never on the trust boundary (the diversity is one weighted judge spawn per FRD gate, not per WO).
- **balanced** (Max 5x): up to 4 work orders in parallel within a feature; judge (review) on opus, workers on sonnet.
- **powerful** (**default**, Max 20x): up to 8 in parallel — the default; finishes sooner.
- **deep**: best model everywhere, split team, extra adversarial review. Slowest/most expensive (it intentionally narrows the wave — opus + split is heavier per slice, so fewer run at once).

**How a run stops (DR-050, owner decision 2026-06-16).** By default the build runs to **completion** — it does NOT stop after N features ("stop after N" protects neither tokens nor progress: one feature can cost 10x another). A run stops only when: (a) **nothing is left** to build, (b) the **budget ceiling** is reached — `maxAgents` (a hard cap on subagents spawned, **the real overnight guardrail**) or a `+Nk` turn directive / `maxSpend`; **for overnight runs always pass `maxAgents`** (counted inside the engine, it brakes even if `budget.spent()` under-counts or the supervisor dies), (c) **too many features block in a row** (a health breaker), or (d) what remains **needs you**. `maxFrds` bounds a supervised **test** run and counts features **processed** — built + blocked + **reopened** — so a reopen counts and chained reopens can't slip past the cap (a real bug the 2026-06-16 overnight test caught). `maxFrds` is never the overnight guardrail; `maxAgents` is.

> **This SOP is Claude-only, like every other build path.** No non-Claude runtime may run an attended,

### Launch checklist (run in order — mechanized, not prose)
1. **Preflight (read-only):** `bash "${CLAUDE_PLUGIN_ROOT}/scripts/preflight-implement.sh" <projectDir> --target-runtime claude --run-mode auto`. Every line must read `PASS` (exit 0), including the logical build-run intent classification from the shared resolver; it never asks the owner for an ID. A `FAIL` STOPS the launch: *another build ACTIVE* → abort; *STALE LOCK* → it prints the reset commands (it never auto-resets — the next step's `launch-implement.sh` takes a fresh lock); a readiness/overlay/`NEEDS CLARIFICATION` fail routes back to `/pandacorp:architecture` or `/pandacorp:upgrade`.
2. **Resolve the logical run + take the lock:** `bash "${CLAUDE_PLUGIN_ROOT}/scripts/launch-implement.sh" <projectDir> <mode> <maxAgents> [auto|new|continue-run-id] [--frds <comma-list> | --change <card>] [--max-frds <N>] [--max-spend <N>] [--ttl <seconds>] [--parallel-gates | --no-parallel-gates] [--gate-slots <1-8>] [--gate-evidence explore|digested] [--gate-context-scope] [--drift-finder on|off] [--gate-inventory-cache] [--lane fast|classic] [--review-budget now|defer] [--lanes <N>] [--resume <run-id>]`. The first four arguments remain backward-compatible. `--resume <run-id>` is only for a run cut short whose lease went stale (see **Resume after a usage limit** below). The **fast lane is the default since 9.119.0** (DR-124): omit `--lane` for it (the launcher still passes `args.lane:'fast'` explicitly); `--lane classic` opts out (when: §The fast lane below). `--review-budget defer` (fast lane only, refused with `--lane classic`) stops it at USABLE; pass it only when the owner asks to review later. `--lanes N` (fast lane only, refused with `--lane classic`) sets the run's lane ceiling; omit it (the default: K = 1, lanes off until the FM-5 bench passes) unless the owner asks for lanes (`--lanes 2`, capped by mode, re-decided every round from the ready width) or for a number. `parallelGates` is **ON by default since v9.116.0** (engine `args.parallelGates` — see the constants table below); pass `--no-parallel-gates` only when the owner asks for the legacy single-gate-worktree topology (`--parallel-gates` still works to make the now-default choice explicit in a launch's own argv). `--gate-evidence digested` sets `args.gateEvidence` (WP-06: a MECH collector pre-gathers each gate's evidence in its pinned worktree; the engine default is `explore`); pass it only when the owner asks for it (a canary). The three gate-cost levers of the table below reach the engine the same way, never by hand: `--gate-context-scope` → `args.gateContextScope: true`, `--drift-finder on|off` → `args.driftFinder: true|false` (omitted → the engine default: on under `digested`, off under `explore`), `--gate-inventory-cache` → `args.gateInventoryCache: true`; any other value fails before the lease is taken. `--ttl` overrides the atomic lease's TTL (default 3600s — BL-0153: raise it further for a targeted single-FRD/change run expected to spend long stretches inside one gate/repair chain with no intervening safe-point to renew at); leave it unset for the normal case. A targeted request MUST be passed through the named flag; `--frds` and `--change` are mutually exclusive and invalid/escaping paths fail before lease acquisition. The shared resolver automatically reuses the canonical `build_run_id` only for a safe cross-runtime cold continuation: `phase: implementation`, `running: false`, no lease, a valid prior ID, and `build_runtime` different from the runtime being launched. The owner never copies or chooses that ID. Otherwise the launcher creates a new governed run. A same-runtime next pass and a project already in `phase: release` are new runs; when the owner's request explicitly says to start a separate/reset budget run, pass `new` as the fourth argument. An explicit prior ID is reserved for a runtime supervisor's mechanical restart receipt, not owner interaction. Before taking the lease, the launcher resolves the installed `pandacorp-build-state.mjs` to a canonical absolute regular file and passes it as `args.stateCli`; installed Workflow subagents must use that explicit capability and never reconstruct it from `CLAUDE_PLUGIN_ROOT`. The launcher then writes `phase: implementation`, `running: true`, `run_started_at`, touches `.pandacorp/run/build.lock`, and PRINTS the exact JSON-safe `Workflow()` call—including the state CLI and every requested scope/ceiling—to run next. Never add a missing option by hand.
3. **Launch the workflow:** run the exact printed `Workflow({ scriptPath: '<projectDir>/.claude/engines/pandacorp-build.js', args: { mode, maxAgents, projectDir, project, leaseToken, leaseEpoch, stateCli } })` — `args` a real **JSON object**, never a string. **CAPTURE the run id it returns** (the `wf_…` id) and keep it for the whole run — the external maxAgents brake needs it to locate the run's transcript dir (§external brake below), and the same directory feeds the per-run cost/token rollup at shutdown (§Per-run cost/token rollup below, BL-0096).
4. **ARG-ECHO VERIFICATION — its own step, never skipped:** the engine's FIRST log line must read `· maxAgents <N> ·`. If it says `maxAgents OFF` (when you passed one) or `args arrived as a <type>, NOT an object`, the args were DROPPED and the run is UNBOUNDED → `TaskStop` it immediately and relaunch (re-pass args; hardcode the scope into `args` if needed).
5. **Mount the supervisor:** Monitor + the **dedicated ~2-min `ScheduleWakeup` heartbeat** + `PushNotification` — per the detailed steps 1–2 below.
   The dedicated heartbeat MUST renew the atomic lease on every tick using the exact `leaseToken` and `leaseEpoch` printed inside the launcher's Workflow args: `node "${CLAUDE_PLUGIN_ROOT}/scripts/pandacorp-build-state.mjs" renew --project <projectDir> --token <leaseToken> --epoch <leaseEpoch>`. A failed renewal means ownership was lost: `TaskStop` the workflow and do not mutate anything else. Never copy either credential to events, commits or owner-facing summaries.

| Frozen threshold (no activity) | **~15 min** |

| `MAX_REOPENS` per WO | **3** ⇒ then `BLOCKED: needs-owner` |
| Foundation repair cap | **2** internal cycles |
| `maxFrds` default | **unlimited** (opt-in cap, supervised TEST runs only) |
| `maxAgents` unit | **cost-weighted** (opus ≈ 3 units), bounded overshoot ≈ one expensive WO (**~11 units**) |
| `lane` (engine arg; launcher `--lane fast\|classic`) | **`fast`** by default since 9.119.0 (DR-124; sub-defaults `mechScript`, `infraGuard`, `fusedStart` on, `reviewBudget` `now`); `--lane classic` is the opt-out, byte-identical — see §The fast lane |
| `lanes` (engine arg; launcher `--lanes N`, fast lane only) | **1 (off) by default**: lanes ship behind `--lanes N` until the FM-5 bench passes (proposal 40 §7 row 5, §9). `N ≥ 2` is the run's ceiling, capped by mode (pro 1, balanced 2, powerful/deep 4), **auto 1** when the DAG is narrow throughout or the work off its longest path is below the pool bootstrap; each round's K is then min(ceiling, ready width) — a narrow round builds on `main`, a wide one in the lanes; `--lanes 1` = the default made explicit. Each lane round, lane build and landing is a spawn: at K ≥ 2 size `maxAgents` for ~4 extra cost units per chain (the `lane-next`/`lane-mark`/`land-chain` relays) and one snapshot verify per FRD — see §The fast lane, **Worktree lanes** |
| `parallelGates` (engine arg; launcher `--parallel-gates` / `--no-parallel-gates`) | **on** by default since v9.116.0 (D1, BL-0186; canary F1/F2 verdict — the gates stopped being the cost/time bottleneck: 0 drops to the legacy path, 0 idle slot-minutes, unchanged recall parity, ~0.3-0.4 $/run overhead — adopted despite neither canary meeting the pre-registered ≤60 %-of-serial time bar, see `docs/reviews/canary-f2-report.md` §6). On: up to `gateSlots` FRD gates **review at once**, each in its own worktree `.pandacorp/run/gate-worktree-<k>` with its own e2e port (`3800+10·k`); only FRDs with disjoint artifacts gate together, and a dependency orders only the landing (a dependent gates alongside its upstream and lands after it — BL-0194); verdicts land on main **one at a time, in arrival order**, with a stale-pin re-verify (`verify.sh --since <pin>`) before a PASS is stamped. A time lever for multi-FRD runs only — same agents, same cost per gate. **Budget it: `maxAgents` ≥ 8 + 20 × the FRDs the run will gate (24 with the drift finder), PLUS ~4-6 per work order to build** — measured, not a rule of thumb: bench A-1 (ONE FRD / 3 WOs / one reopen) needed **~48 cost units**, and the old "15 × FRDs" floor (= 15 for that run) stopped it at `agents` before any gate. The drift finder (`--drift-finder on`, or `--gate-evidence digested` unless `--drift-finder off`) adds ~4 per FRD (one sonnet unit + one MECH snippet check per gate link, again per re-gate, BL-0207/BL-0214). **Or pass `auto` as `maxAgents` (opt-in):** after the plan the engine computes the projection (`projectedRunCost`), sets the cap to ⌈1.25 × projection⌉, logs the units and an approximate USD (≈ 0.5 USD per unit), and recomputes it whenever the plan grows (a drained change adding FRDs raises the cap, never lowers it). An **explicit integer is never overridden and never fails fast** — below the projection it only gets an `AgentBudgetAdvisory` log (a deliberately partial, resumable run is legitimate, DR-050/070). `auto` is a convenience, **not an owner-chosen budget**: the launcher's "OVERNIGHT run MUST pass one" warning still fires for it, so an unattended run still names an integer. `launch-implement.sh` warns below the floor whenever parallel gates is not explicitly off (advisory; it changes nothing the engine does), and the engine itself logs a one-shot `AgentBudgetAdvisory` when 80 % of `maxAgents` is spent with work still pending (and another when less than one reopen ladder remains). Gates keep launching into free slots while a verdict lands (BL-0192), so budget, not the lane, is what caps throughput. Full contract: `factory/standards/build-orchestration.md` §5c |
| `gateSlots` (engine arg; launcher `--gate-slots`) | **2** (integer 1..8; alias `maxParallelGates`); read only with `parallelGates`. The default matches the 16 GB machine the red-team measured; raise it only on a bigger one. A second concurrent gate is deferred (`gate deferred: agent budget`) when `maxAgents` cannot cover it + its landing |
| Fixed pre-wave overhead (`powerful`, UI project) | **~8 units bare / ~11 with `--change`** (precheck 1 + plan 3 + safe-point 1 + foundation-gate 3, +3 more for `process-change`) — BL-0173: a `maxAgents` at or below this floor collapses the FIRST wave to exactly 1 WO regardless of how many are really ready and disjoint (`launch-implement.sh` warns below `~15` in `powerful` mode; `pickDisjointWave`'s own log names the real cause as `presupuesto de agentes agotado`, distinct from a real dependency/count-cap stall) |

The owner runs `implement` and leaves, even overnight. For that to be SAFE — **no silent stalls, no burning the week's tokens** — launching the build is **never** just firing the workflow. It is **two things, always**:

1. **Launch + set the ceiling** — the **Launch checklist above** already mechanizes this; don't hand-build any of it. `preflight-implement.sh` asserts the conditions, then `launch-implement.sh` writes `phase: implementation` (the ONE place the architecture→implementation transition is set — DR-032; idempotent on a resume), `running: true`, `run_started_at`, clears `supervisor_heartbeat`, drops the phase-aware build lock (`.pandacorp/run/build.lock`, DR-063 — its freshness tells the Stop gate a build is active), pins `projectDir`/`project` (BL-0022 — the engine cds every subagent there and stamps events/`track.jsonl` with it, so launching from ANY cwd is safe), and **prints the exact `Workflow()` call**. **Run that printed call verbatim — never hand-construct it** (no `$(pwd -P)` juggling): the engine's shim `JSON.parse`s the `args` string a `scriptPath` launch delivers, failing LOUD on an unparseable one. Then complete the ARG-ECHO verification (Launch checklist step 4 — a hard gate) and, for an **overnight run, always pass `maxAgents`** (the real guardrail — §How a run stops). Each FRD verified is an immutable commit (the safe point is a commit, never an agent state).
2. **Mount the supervisor** (this is the part that was missing and let a build run >1h unwatched):
   - **Live watch (`Monitor`)** — a bash poll (~2 min; **costs no tokens** — only an emitted *event* wakes the agent) over `.pandacorp/status.yaml` (FRD progress), the run's journal mtime + active agents (frozen?), and the agent count (spend proxy), **and the working tree's git health** (`git status --porcelain` — any `UU`/unmerged path or a `<<<<<<<` conflict marker means a BROKEN tree, a first-class failure signal, DR-067). It emits an event on: a FRD verified, **frozen** (no activity ~15 min), a new block, **a broken working tree** (unmerged paths / conflict markers, DR-067), **pace below target**, or run end. Cover the failure signatures, not just success ("silence is not success"). **Write `supervisor_heartbeat: <ISO timestamp>` to `status.yaml` AND refresh the build lock (`touch .pandacorp/run/build.lock`, DR-063) on every event tick — AND on a DEDICATED ~2-min `ScheduleWakeup` cadence, never ONLY when a Monitor event fires** (a healthy-but-quiet build emits no events for long stretches, so an event-only heartbeat freezes and the build looks dead — the exact audit failure): the heartbeat/lock-touch is a timer, not a side effect of activity. Both are liveness signals: as long as the supervisor is alive the heartbeat stays fresh (< 10 min) and the Stop gate keeps standing aside; if the supervisor dies, the heartbeat AND the lock go stale together and the next `implement` auto-clears the lock while the Stop gate auto-re-engages (same 10-min TTL). **Every staleness reader crosses `supervisor_heartbeat` WITH `last_event_at` (the producer's own clock, DR-066): the build is LIVE if EITHER is < 10 min old, and STALE only when BOTH are older** — so a quiet supervisor whose engine is still advancing `last_event_at` at safe points is never misread as dead (this is what `preflight-implement.sh` and `verify-before-stop.sh` both enforce).
   - **Positive heartbeat to the event stream (observability fidelity, DR-066).** A frozen `running: true` is **not** proof of life — a monitor reads liveness as `running AND fresh`, so the supervisor must keep the freshness signal genuinely alive, not just flip a flag. On **every tick** (and on the time-driven beat below), besides writing `supervisor_heartbeat`, **append a positive heartbeat event to the stream** so "sin señal" (no events at all) truly means *hung*: `printf '{"event":"SupervisorTick","at":"%s","project":"%s","data":{"running":true}}\n' "$(date -u +%FT%TZ)" "$(basename "$PWD")" >> ~/.claude/dashboard-events.ndjson` (fire-and-forget). The **engine** already advances `last_event_at` in `status.yaml` at each safe point (FRD gate, sync) and appends `AgentWorking` events per agent — together they are the producer's positive heartbeat. The consumer (Mission Control) crosses `running` with this recency and declares its own freshness (en vivo / datos de hace X / sin señal). See `factory/standards/observability.md` "Liveness & freshness fidelity".
   - **Health heartbeat — a VISIBLE message to the owner every ~20–30 min, even with NO anomaly.** The Monitor only wakes on events, so the supervisor must schedule this latido SEPARATELY (a `ScheduleWakeup` timer) — never rely on events for it, or a healthy-but-quiet build looks dead. **The same time-driven tick also advances `supervisor_heartbeat` + appends a `SupervisorTick` event (DR-066)** so the freshness signal never freezes between long, quiet agents (the exact audit failure: the build advanced while the heartbeat stayed frozen). Each heartbeat states: WOs done/total, the FRD in progress, rough spend so far, and "all green". **Silence reads as "stuck" to the owner** — a periodic "still going, X/Y done, ~Nk output spent, all green" is the entire point.
   - **Notifications** — the engine fires a macOS desktop notification (`osascript`) on every alarm; the supervising agent ALSO sends a `PushNotification` to the phone (when Remote Control is on). No third-party push app (owner decision 2026-06-16). The owner is asleep, so reach BOTH the desktop and (if available) the phone.
   - **Announce each FRD (milestone)** — on every FRD **verified**, send the owner a visible message (+ push): the FRD name, one line on WHAT it does, the **route/page to try it**, and X/Y done. Don't make the owner ask "is it done yet?" — tell them at each milestone, and point at the review worktree (below) so they can actually open it.
   - **React to every event, repairing before giving up** — a stall → unstick it; a **broken working tree** (unmerged paths / `<<<<<<<` markers) → **discard its uncommitted edits** (a surgical restore of the project's own dirty files to `HEAD` — never to `last_green_sha`, which would also stage the reversal of every commit made after the pin — never touching paths outside the project, BL-0202 — bounded auto-repair; NEVER hand-resolve a stash-pop, DR-067) and let the run rebuild the lost between-safe-point work; a failing feature → the engine itself runs a **repair pass** (diagnose + fix) before it ever blocks. Only when a fix is genuinely out of reach does the feature go **BLOCKED with a reason** and the build moves on to independent features: `needs-owner` (a human must act — env var, secret, external account, product decision; also logged to `.pandacorp/inbox/decisions.md`), `external` (internet/upstream — retried later), or `error` (unresolved technical fault). The supervisor escalates `needs-owner` to you immediately; for a budget/health stop it **stops the build and notifies** with the detail ("blocked at FRD-X because Y, come decide").
   - **Self-learning of avoidable stalls (DR-047)** — when the supervisor unsticks something, **classify it**: uncontrollable (internet, server 500) → nothing to learn, don't capture; **avoidable** (a recurring pattern, an engine bug, a config) → capture the lesson to `factory/memory/_inbox.md` and, if fixable factory-wide, **fix it on the spot** so it never recurs. Every avoidable stall makes the factory better.
   - **Budget ceiling** — the engine stops at `maxAgents` (counting the subagents it spawns, checked at every FRD **and build-wave** boundary — DR-070, the fine-grained brake) and `maxSpend` is a secondary `budget.spent()` ceiling. **The in-engine counter is NOT trusted alone (DR-070)** — it once silently under-counted and blew past the cap. So the supervisor enforces a **reliable EXTERNAL brake**: each tick it counts the actual `agent-*.jsonl` transcript files the Workflow run wrote. **The REAL path (verified 2026-07-07 against live runs):** `~/.claude/projects/<project-slug>/<session-id>/subagents/workflows/<run-id>/agent-*.jsonl` — where `<project-slug>` is the LAUNCHING session's cwd with every `/` replaced by `-` (leading dash included: `/Users/Shared/Proyectos/personal-page-v2` → `-Users-Shared-Proyectos-personal-page-v2`), `<session-id>` is this Claude Code session's id, and `<run-id>` is the `wf_…` id the `Workflow()` launch returns — **capture that run id at launch (Launch checklist step 3) and keep it for the whole run.** If you didn't capture it, resolve it at tick time as the NEWEST `subagents/workflows/wf_*` dir under the session transcript root. Count with `ls ~/.claude/projects/<project-slug>/<session-id>/subagents/workflows/<run-id>/agent-*.jsonl 2>/dev/null | grep -v '\.meta\.' | wc -l` and, past `maxAgents` (allow a small overshoot for the in-flight wave), it `TaskStop`s the workflow + runs the guaranteed shutdown — independent of the engine counter and of `budget.spent()`. **DIVERGENCE to know (DR-070): inside the engine `maxAgents` is COST-WEIGHTED (an opus spawn counts ≈ 3 units, so an escalation can't silently blow the budget), but this EXTERNAL brake counts RAW transcript files (1 per spawn, unweighted).** So the external file count is a conservative *over*-estimate-proof floor that trips a bit later than the weighted engine cap — that's intended: the external brake is the fail-safe backstop for a dead/under-counting engine, not a second precise meter. Size `maxAgents` to the weighted cost; the external brake will still catch a runaway. The supervisor also treats `maxAgents` as the **cumulative-across-passes** walk-away budget: it does **not** relaunch the next pass once cumulative agents reach the ceiling — it stops and notifies the owner with the balance. Always pass `maxAgents` for an unattended run — and remember one pass over many FRDs can legitimately cost ~3–5 agents/FRD, so size the cap to the FRDs you expect to process, not to a single number that one pass blows through.
   - **Relaunch for multiple passes** — a run makes ONE pass over the pending FRDs; WOs a gate **reopens are deferred to the NEXT run**. Every terminal path releases its lease, so a same-runtime next pass goes through the full preflight + `launch-implement.sh` again and receives a NEW logical run/receipt. A cross-runtime launch at that released implementation safe point is instead auto-classified as a cold continuation and inherits the prior logical run ledger. Never relaunch the Workflow directly and never reuse a released token/epoch. `VERIFIED` frontmatter prevents rework across passes.
   - **Resume after a usage limit (both lanes).** A run cut by a usage limit (or a crash) before it released its lease leaves a STALE atomic lease under its own `build_run_id`, and a plain relaunch fails CONTENDED. Never run `pandacorp-build-state.mjs reclaim` or compose the Workflow args by hand: (1) preflight with the cut run named, `preflight-implement.sh <projectDir> --target-runtime claude --run-mode auto --continue-runtime claude --continue-run-id <build_run_id>` (it PASSes only for a stale lease of that same runtime and run); (2) `launch-implement.sh <projectDir> <mode> <maxAgents> --resume <build_run_id>` plus the cut run's own flags (a cut classic run resumes with `--lane classic` again; passing that run id as the positional fourth argument does the same). The launcher performs the fenced reclaim itself — stale (past its TTL and the BL-0153 grace window), runtime `claude`, the same run id — and prints the normal `Workflow()` call with the NEW `leaseToken`/`leaseEpoch` (the cut run's token is dead). A fresh lease, another run's or another runtime's is refused (exit 2) and left untouched. Then continue from step 3 of the Launch checklist. The fast lane's resume precheck (§The fast lane) and the classic baseline then pick up from the committed state.
   - **Stop the LOOP vs stop a run (DR-068).** Stopping a single workflow **run** (TaskStop / the run ends) does NOT stop the build — the supervisor's job is to **relaunch the next pass**, so a lone stop just triggers another pass (the exact confusion the owner hit: "I stopped it but it came back"). To stop the **whole build**, the owner sets the stop signal — **`rethink_pending: true` in `status.yaml`** (or drops `.pandacorp/run/stop`); the supervisor checks it **at each safe point AND before every relaunch**, and when set it **halts the loop** (does not relaunch) and runs the guaranteed shutdown below. Surface this to the owner: "to stop the build, set `rethink_pending` / run the stop signal — not just stop a run."
   - **Per-run cost/token rollup (BL-0096) — right before the guaranteed shutdown below, once per pass.** Neither the engine's cost-weighted `maxAgents` counter nor `dashboard-events.ndjson` carries a single $ or token figure (the E5 slim-payload precedent is deliberate — never widen that stream to add one). The ONLY place a pass's real spend is recorded is here: using the SAME transcript directory the external maxAgents brake above already resolves (`~/.claude/projects/<project-slug>/<session-id>/subagents/workflows/<run-id>/`, from the captured run id), run `node "${CLAUDE_PLUGIN_ROOT}/scripts/usage-rollup.mjs" --dir <that-directory> >> <projectDir>/.pandacorp/track.jsonl`. This is a deterministic CLI (never re-derived by hand) that parses that run's OWN `agent-*.jsonl` subagent transcripts (which carry `message.model` + `message.usage` — verified against real transcripts 2026-09-03) and prints ONE `usage_summary` line — per-model call counts, token totals and a cost estimate from the published per-MTok rates (`docs/proposals/33-model-era-audit.md` §3) — appended fire-and-forget, exactly like every other `track.jsonl` line. It fails loud (nonzero exit, no line printed) on a genuinely corrupted transcript rather than silently rolling up an empty/zero summary; that failure is non-fatal to the shutdown itself (best-effort telemetry) — note it in the pass's Spanish progress summary and continue. Full shape: `factory/standards/build-orchestration.md` "Durable build timeline". The summary also carries each agent's REAL `tool_calls` (from its transcript; an agent's own self-reported count is reconciled against it, never trusted — BL-0208), a `by_category` cost split by engine label (`gate`, `patch`, `find:drift`, …) and an always-present `gate_test_repair` block (BL-0210) — a canary comparison states `gate_test_repair.fired` for both sides.
   - **Post-run `last_green_sha` audit (BL-0190) — same spot, once per pass, right after the rollup.** A `last_green_sha` publication certifies every commit since the previous pin, and the scheduler also lands build waves of FRDs no gate has judged yet (parallel gates, safe-point drains, retry rebuilds), so a pin can vouch for unreviewed work. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/audit-last-green.mjs" --project <projectDir> --last 10 --record` (a deterministic CLI, never re-derived by hand): it walks the project's publication commits and the `track.jsonl` timeline, flags every certified FRD commit whose FRD was not VERIFIED at that publication (with the minutes until it was), appends ONE `last_green_audit` line to `track.jsonl` (a kind the timeline reader ignores), and exits 1 on a violation and 2 when it cannot read its inputs (fail-loud, DR-078). It only audits: it never rewrites history and never blocks the shutdown. On exit 1 name the violations (publication, commit, FRD, window) in the pass's Spanish progress summary; on exit 2 say the audit could not run and why. The owner decides whether a violation matters: it is harmless once that FRD verifies, but until BL-0212 lands a REVERT of that FRD's work order "to `last_green_sha`" restores its own rejected code (the pin already contains it), so name any reopened/blocked FRD among the violations. Canary E's criterion "0 audit violations" is this script's count.
   - **Guaranteed shutdown — `running: false` on EVERY exit, never a lying flag (DR-068/BL-0068).** Whenever the supervisor's loop ends FOR ANY REASON, its guaranteed last act clears state through the governed lease operation. The engine detects `.pandacorp/run/stop` only through the fenced Node `inspect-stop` receipt — never ambient shell `test`/`[`/aliases. Every pre-loop early return invokes the capability-bounded `close-preloop` command: it rejects product/staged drift, mutates and commits only `.pandacorp/status.yaml`, then finalizes the lease and returns an allowed-path receipt. The MECH runner is not an implementer and must run that one command only. A stale `running: true` is still never trusted as alive: readers cross it with `supervisor_heartbeat` recency, and a hard-killed supervisor falls back to lease/heartbeat TTL recovery.
- **Auto mode (permissions), not babysitting**: the owner activates Claude Code's *auto mode* (Shift+Tab, or `defaultMode: "auto"` in THEIR `~/.claude/settings.json`). NEVER `--dangerously-skip-permissions`.
- **Review worktree — let the owner SEE the latest green version without touching the build.** Keep a worktree pinned at the last green under the **canonical review-worktrees root** (DR-090 — `/Users/Shared/review-worktrees/<project>`, a `Shared`-level sibling of `Proyectos/`, named after the project, NOT inside `Proyectos/` and NOT inside `.claude/`): `git worktree add /Users/Shared/review-worktrees/<project> <last_green_sha>` with its OWN `node_modules` (`pnpm install` there — NOT a symlink, which breaks Next's HMR/watcher), and update it (`git -C /Users/Shared/review-worktrees/<project> checkout <new last_green>`) each time an FRD verifies. The build keeps running untouched on the main checkout. To view it, the owner opens a **Claude Desktop session in that worktree** (its Preview button serves it natively — the build session's Preview can't point at an external worktree, confirmed) OR asks the supervisor to bring up its dev server on a fixed port **on-demand** and hands back the URL. Do NOT keep a permanent dev server that restarts on every FRD (Next's file watcher is flaky across `git checkout`). Subagents that must mutate in parallel can use `isolation: 'worktree'`.
- **Internal gate-worktree residue is evidence (BL-0067).** Never delete, reset, prune, recreate or force-remove `.pandacorp/run/gate-worktree`. The engine reuses it only when Git records the exact path and it is clean; otherwise it preserves the residue and falls back to the synchronous gate.

## The fast lane (the default since 9.119.0, DR-124 — proposal 39)

**The default build.** A plain `launch-implement.sh <projectDir> <mode> <maxAgents>` runs the fast lane (sub-defaults: scripted MECH ops, the infra guard, the fused start, `--review-budget now`); ARG-ECHO must then show the engine log line `lane fast · mechScript on · infraGuard on · reviewBudget <now|defer> · lanes <N|auto>` (no such line = the args were dropped and the classic lane ran: stop and relaunch). Measured on the small bench (`docs/proposals/39-fast-lane-implement.md`): USABLE at 8.0 / 11.8 min with the independent oracle 151/151 both at the USABLE commit and at the final VERIFIED commit, the full VERIFIED + close-out at 40.3 / 43.8 min and ~17-19 $-eq, against 51-84 min and ~24-30 $-eq for the classic lane (a vanilla single agent: 2.6-5.5 min, unreviewed).

**When to choose `--lane classic`** (the opt-out; the plan agent, global parallel waves of per-WO builders and commits, the gate before anything counts, exactly as before): only when the owner asks for it, or when (a) most of the build is **floor** code (auth, payments, personal data, secrets, destructive data operations) so USABLE would rarely apply and the classic waves' parallel builds win; (b) many independent FRDs could build in parallel and the owner wants the shortest time to all-VERIFIED rather than the first thing to try; or (c) the owner wants nothing on `main` that has not passed its gate. Resume a cut classic run with `--lane classic` again.

**What it does differently.** At K = 1 (see **Worktree lanes** below) FRDs build **one at a time, on `main`**, in dependency order. The start is ONE scripted `fast-start` op (precheck, owner stop/rethink, the baseline verdict, the plan, the rollup sync and the first dispatch; any unusual start hands back to the separate steps). Per FRD: no plan agent (the Build Plan order is read by a script), ONE builder holding every work order's brief, `difficulty: high` included (only a WO that already failed once gets its own opus builder), which runs `verify.sh` itself before it returns, and each WO is committed by the scripted `pandacorp-build-mech.mjs commit-wo` (it refuses undeclared edits, uncited ACs and another WO's frontmatter; it stamps `IN_REVIEW` and commits code + stamp as ONE commit). A WO that cannot land is **parked** (`park-wo`: its files go to `.pandacorp/run/salvage/<wo>/`, the tree is reset) so the next WO never builds on broken files. Then ONE scripted `verify.sh` on the clean landed tree. The FRD's unchanged opus gate (DR-015) then runs in a parallel gate slot, pinned to that landed SHA, while the next FRD builds; the security audit starts alongside the first gate and the close-out audits only the delta since.

**Worktree lanes (`--lanes N`, proposal 40 Phase B).** Whether a run lanes is decided once, after the first safe point drained every ready change card into the schedule (a bare run, `--frds` and `--change` share this scheduler), on the run's ceiling: `--lanes N` (no `--lanes`: K = 1, lanes off, no lane op at all, until the FM-5 bench passes), capped by mode (pro 1, balanced 2, powerful/deep 4), and **1 when the DAG is narrow throughout or the work beside its longest path is below the pool bootstrap**, so a typical one-FRD change runs exactly as above. K itself is **re-decided at every scheduling round**: min(ceiling, the ready width now), so a run that starts one work order wide builds that chain on `main` and goes parallel as soon as the DAG widens (bench FM-5 built sequentially when K was decided once). At a ceiling ≥ 2 the engine boots the worktrees under `.pandacorp/run/lanes/` at once, beside the first work, and builds **chains** (≤ 3 work orders of one FRD along a linear stretch of the DAG, longest downstream path first; any FRD's work order whose dependencies are met can take a lane) in parallel, each with the same builder and `commit-wo` per WO on its own `lane/<chain>` branch and its own server port, read by the Playwright config from the lane's `.pandacorp/run/lane.env` on disk (a lane never tests a sibling's server, even from a shell that never sourced it). A chain touching `prisma/**`, migrations, `package.json` or a lockfile is a **barrier**: it builds on `main` and lane landings wait for it. Built chains **land one at a time** (`land-chain`: rebase keeping one commit per WO, journals merged by union, `messages/*.json` by key, tsc/biome/related unit tests, fast-forward). Once an FRD's last chain lands, USABLE is one full `verify.sh` on that pinned SHA in a snapshot worktree while landings go on; a red result is bisected over the chains landed since the last green pin and fixed forward on `main` (sonnet, then opus), never reverted: still red → `BLOCKED: needs-owner`. A chain still unbuilt after 3 attempts is **parked**: only its DAG descendants wait (the run reports the blocked FRDs at once; they are deferred to the next run, not BLOCKED). The next run retries it fresh; any WOs it had committed but not landed are kept under `refs/lane-parked/<chain>/` first, never reset away. A usage limit pauses every lane at once (`paused-infra`, no attempt counted, nothing parked); the resume re-dispatches each live chain on its own lane from its last committed WO. The run result carries `lanes: { k, parked, blockedFrds }`.

**USABLE vs VERIFIED — tell the owner which one.** In the owner's words: USABLE = "ya lo puedes probar; está construido y verde, pero el revisor aún no lo ha certificado"; VERIFIED = "revisado y certificado por el gate". Never present a USABLE FRD as done or releasable.
- **USABLE** = every WO of the FRD is committed on `main` and `verify.sh` is green on that clean landed SHA, for an FRD the deterministic product-risk floor (`classify-change.mjs --product-floor`, run on the plan and again on the landed diff; never lowered) marks **non-floor**. It is a `build_usable` event (track.jsonl + dashboard) and a push to the owner ("you can try it now"); it is **not** a review verdict and it never advances `last_green_sha`.
- **VERIFIED** = the FRD passed its opus gate, exactly as in the classic lane. Only VERIFIED advances `last_green_sha`, and the review worktree keeps showing the last VERIFIED snapshot.
- A **floor** FRD (code touching auth/session, payments, persistence of personal data, secrets/env, or destructive data operations — or an unreadable classification, fail-closed; prose, test fixtures and framework config never count, `factory/standards/build-orchestration.md` §5d) is USABLE only when VERIFIED, and an FRD that depends on a floor FRD waits for that VERIFIED before it builds.
- **After USABLE the gate's ladder is fix-forward only:** a rejection is patched and re-certified (DR-073); a discard of USABLE code becomes `BLOCKED: needs-owner` with a decision record and a push, and nothing is reverted. If the owner approves the discard, revert the whole dependent set named in the record at once, never part of it.

**Review debt** = the FRDs whose WOs are all ≥ `IN_REVIEW` but which are not `VERIFIED`. It is **derived when read** (the run result's `reviewDebt`, the work-order frontmatter); nothing stores it (DR-115). Report it to the owner with every USABLE milestone. An external release must not ship with open review debt.

**`--review-budget now|defer`.** `now` (the default) continues to VERIFIED and runs the close-out once. `defer` stops when every buildable FRD is USABLE: no FRD gate is launched and the run ends with `stopReason: 'review-deferred'`, the USABLE list and the review debt. **To pay the debt later**, relaunch normally (the default fast lane with the default budget, or `--lane classic`): every all-`IN_REVIEW` FRD goes straight to its gate, nothing is rebuilt. Either lane keeps the fix-forward-only rule for an FRD that is still USABLE (its latest committed `build_usable` line holds): the fast lane's resume precheck derives that list, and `wo-revert.mjs` derives it again before any discard, so a classic-lane gate rejection of a USABLE FRD ends `BLOCKED: needs-owner` with a decision record, never an automatic revert. Size `maxAgents` for a defer run without the per-FRD gate units (the launcher prints that note).

**Halt and resume on usage limits (`paused-infra`).** An agent that throws, returns nothing, or reports a usage limit, a 429 or an overload is an **infrastructure** failure, never a WO failure: it uses no repair attempt, never marks `BLOCKED`, never reverts. One retry after 60 s; a second infra failure, or any limit signature, **halts** the run: no new dispatch, in-flight work is accepted or parked, in-flight gate verdicts are not landed (those FRDs re-gate on the next run), a `build_paused` event is recorded and the lease is released. The run returns `stopReason: 'paused-infra'` plus a `resumeHint`. Committed WOs are kept. When this happens, tell the owner in Spanish that the build paused on a usage limit, that nothing was lost, and when to relaunch (once the usage window resets); the supervisor does **not** relaunch it in a tight loop. Under a real limit the closing step may fail too: the lease then expires by its TTL, and the next launch resumes it with `--resume <build_run_id>` (**Resume after a usage limit** above: the launcher does the fenced reclaim; never clear it by editing `status.yaml`).

**How to resume (after a usage limit, a crash or a `defer` run).** Run the normal Launch checklist again with the default lane (no `--lane`; the resume precheck is part of the scripted ops, so a `--lane classic` relaunch would skip it), adding `--resume <build_run_id>` when the cut run's lease went stale (**Resume after a usage limit** above). Before anything reads state, the precheck finishes interrupted reverts, commits the journals' pending lines, salvages engine-owned dirt to `.pandacorp/run/salvage/` and resets it (an owner edit in a work order is kept; only its `implementation_status` goes back to the committed one), then checks every `IN_REVIEW` WO: it counts only if `HEAD` holds a commit flipping it to `IN_REVIEW` after its last `IN_PROGRESS` dispatch stamp; otherwise it is demoted and rebuilt. Previous runs' committed work is never rebuilt and a `defer` run's debt stays debt.

## How it runs

`pandacorp-build` is a native Claude Code JS engine (plain script code in `.claude/engines/`, launched only by `scriptPath` from this skill — never an owner command) that orchestrates each run deterministically. The classic lane (`--lane classic`) is described here; the default fast lane reuses the same gate, recovery ladder and close-out with the build shape of §The fast lane: **baseline self-heal** (discard a dirty/conflicted tree's uncommitted edits — restore them to `HEAD`, never to `last_green_sha` — and clean temp pages, leaving every stash, DR-067/BL-0202; then repair a red `verify.sh` before planning) → **plan** (read every FRD's frontmatter + Build Plan; return non-`VERIFIED` FRDs in cross-FRD order) → **global-wave build** (§Execution modes above) with **one review + integration gate per FRD** and the patch-first → self-repair → revert+reopen recovery ladder. It is app-agnostic — it depends only on the docs' state and the project's `verify.sh`. The step-by-step is §Per-FRD loop below; the depth is `factory/standards/build-orchestration.md`. Two facts the runtime needs that live only here:

**`reviewSplit` — the FRD gate, in four parallel lenses.** In `powerful`/`deep` mode the per-FRD gate fans out into four read-only finder lenses (correctness vs the EARS AC, security, quality/duplication, runtime-visual) running in parallel; their findings are deduped, each surviving CORRECTION is adversarially verified by a skeptic that tries to refute it (a refuted finding dies), and a single Opus closer reviews only what survived — independently confirming each correction, running `verify.sh --since`, and applying the same DR-072 correction-vs-nit split verdict as the serial gate. `pro`/`balanced` keep the plain serial reviewer, unchanged. If the split's estimated cost doesn't fit the remaining `maxAgents` budget, or all four finders die, the engine falls back to the serial gate — the gate itself is never skipped.

**Resume is frontmatter-driven, not run-id-driven.** A relaunch reads `implementation_status` off disk: a `VERIFIED` work order is never rebuilt, and one left `IN_REVIEW` goes straight to its FRD gate instead of being rebuilt from scratch. There is no in-memory "where was I" — the tree IS the memory. A run makes ONE pass over the pending FRDs; the supervisor (Monitor + ScheduleWakeup + PushNotification, §Unattended operation above) relaunches pass after pass — reading the same frontmatter each time — until nothing pending/reopened remains or a budget/health ceiling stops it.

## Per-FRD loop (what each feature goes through)

1. **Build** each work order (coarse — a whole view/capability): the ENGINE stamps `IN_PROGRESS` at wave dispatch (BL-0002 — atomic, so the board never under-reports a busy wave); the builder receives its **context pack (DR-108)** — the WO file path + the verbatim EARS AC lines it owns, extracted once by the planner — implements with TDD, runs its **own** fast self-test (not the whole suite; merged into the builder in solo mode — the FRD gate is the trust boundary, not the self-test), sets `IN_REVIEW`, writes its `## Status Note` hand-off (interfaces exposed, integration seams) so the next agent reads that, not all the code. Mechanical steps (the per-WO commit, the dispatch stamp, safe-point, rollup sync, archive, notify) run on the cheap tier (`MECH`, default haiku — DR-108).
2. **FRD gate** (`reviewer`, a different model from the generator): review the WHOLE feature with the 4 lenses + write adversarial tests the implementers didn't see (DR-015), exercising the work orders **together** (integration); run the **focused** `verify.sh --since <last_green>` (biome+tsc global + only the tests affected this cycle; the browser layer scoped to smoke+shell — DR-106; the full suite runs once at close-out). Green → every WO + the FRD frontmatter → `VERIFIED`, commit. A specific WO wrong → the engine recovers in this order:
   - **Patch-first (DR-073):** attempt an in-place opus patch of the reviewer's specific finding(s) + RED-proven failing test on the EXISTING build, re-gated WHOLE-PROJECT (full FRD tests + a whole-project knip+biome+tsc); an independent verifier stamps `VERIFIED` on clean.
   - **Self-repair budget (DR-107):** a red the patch's own edits introduced — e.g. a type error in its own new test — is fixed in place, up to 2 internal cycles, instead of ending the patch.
   - **Cause-discrimination (BL-0001)** when a patch fails: `cause: 'gate-test-defective'` (the reviewer's adversarial test is internally inconsistent/unsatisfiable) routes to a gate-test repair — an independent reviewer fixes the TEST, never discarding a correct build; `cause: 'code'` falls back to revert + reopen (`PLANNED`, `reopen_count`+1; reviewer-authored / Status-Note-referenced test files are PRESERVED to `.pandacorp/run/preserved-tests/`, never deleted).
   - **Retry budget:** a `cause: 'code'` reopen then gets ONE **in-run retry (DR-107)** — rebuild the reopened WOs NOW from the clean base (opus) + re-gate, instead of paying a whole extra pass; only if that also fails is the WO deferred to the next run. `reopen_count` stays the single attempt budget, capped by `MAX_REOPENS` → BLOCK needs-owner.
   - **Model-escalation (DR-073):** a WO marked `difficulty: high` builds on opus a-priori, and any WO with `reopen_count >= 1` escalates to opus empirically (it already failed once) — never below the mode's floor; `maxAgents` counts each opus spawn as ~3 cost-units so escalation can't silently blow the budget.

   Otherwise (no specific WO to patch) the engine runs a **repair pass** (diagnose + fix); only if that fails does the feature go `BLOCKED` with a `blocked_reason` (`needs-owner` | `external` | `error`) + notify, and the build continues with independent features.
3. **Drain the change queue at the safe point (DR-069) — how the owner talks to a running build. THE ENGINE DOES THIS ITSELF** (audit-20 P0-3: it is cabled in `pandacorp-build.js` as the **safe-point check at every FRD boundary** — it reads `rethink_pending` (stop), the queue's `ready` items (drain via the process-change step) and answered `decisions.md` entries (flip their BLOCKED WOs back to PLANNED); the supervisor no longer carries the drain, it only monitors/notifies). The change was written by a detection-free door, so it's been waiting safely — the build integrates it **at a safe point, never mid-feature**. **Only `status: ready` items are taken; `status: draft` is SKIPPED** (the owner is still working it out — the file is left untouched, DR-069). **TARGETED-BUILD SCOPE (owner incident 2026-07-06): the queue drain runs ONLY on a BARE `/implement` (no `change`, no `frds`). A TARGETED build — launched with a specific `change` or `frds` — implements ONLY its target and does NOT drain other `ready` changes** (they wait for a later bare `/implement`); the engine's `TARGETED` flag suppresses the drain at every safe point (hard JS guard, proven by test-pandacorp-build scenarios 10a/10b, with 10c guarding the bare path). "Implementa solo este cambio" means only that. Routing (encoded in the engine's process-change prompt), work-conserving — never stall the whole build for one item:
   - **`expedite`** first, then **`standard`** FIFO.
   - **autonomous-resolvable** (a clear scoped change) → integrate it via the **`iterate`** engine (feature/change → FRD/work-orders/blueprint, calling `work-orders`/`design`) or the **`bug`** engine (regression test → fix), then it passes the **FRD review/test gate** like planned work (same quality).
   - **needs-owner** (product/money/irreversible/design decision) → write it to `.pandacorp/inbox/decisions.md`, notify, and **DEFER + continue with independent FRDs**; only fully STOP if it blocks everything.
   - **structural / fundamental / new-design** → pause (`rethink_pending`) + tell the owner the command to run (e.g. `/design` for a visual — the design gate is theirs); don't silently rebuild half the app.
   - **Complete = verify the durable record, then ARCHIVE (never hand-delete, DR-069).** The **engine's close-out archive step** does this for every change it integrated whose affected FRDs all VERIFIED: it confirms the durable record exists (the landing commits **touched the canonical docs**), stamps `status: done` + `shipped_sha` + `shipped_at` and **moves the file into `changes/done/`** (the active `changes/` stays pending-only; the file is **moved, never `rm`'d** — the folder is gitignored, so a delete is irreversible), updates the queue index. A change whose FRDs did NOT all verify stays `ready` and is drained again next run. **Never auto-delete** `done/`; any prune is a separate owner-gated, reversible action.
   The engine also honors `rethink_pending: true` at every safe point and inspects `.pandacorp/run/stop` exclusively through the launcher-provided absolute `stateCli inspect-stop` capability. Every recurring safe-point verdict must carry the fenced Node `lstat` receipt; the engine validates it and aborts on a missing/malformed/failed receipt rather than guessing `stop:false`. Shell `test`, `[`, aliases and direct path inference are forbidden. Queue and answered-decision processing stay separate from that stop truth. The next run clears `rethink_pending` only after starting from the re-planned docs. (The former `inbox/bugs/` folds into `changes/` as `type: bug`.)

   **Dynamic Workflows evidence boundary (BL-0074):** workflow JavaScript cannot execute the CLI
   directly, so a Claude subagent transports the receipt. The engine fails closed on invalid evidence
   and the installed qualification proves real execution under hostile aliases; that does not remove
   the platform's model-agent trust boundary. It is a Claude-side hardening item (BL-0074) that stands
   on its own merits; the R10/R11 gates it used to be measured against are suspended (DR-120).

## Real-time documentation (Mission Control reads it live)

Keep updated: each work order's frontmatter `implementation_status`; `.pandacorp/status.yaml` (`progress`, `running`, per-status counts, `last_green_sha`, `safe_to_test`); `.pandacorp/comms/progress.md` (append-only log — what was done, decisions, problems; allows resuming with no prior context). A green gate publishes state with **two commits**: commit A is the complete reviewed snapshot; metadata-only commit B records `last_green_sha: A` + `safe_to_test: true` after proving A exists and is an ancestor of HEAD. Never amend A to try to make a commit contain its own SHA (BL-0066). If something deviates from plan, document it; don't hide it.

**`progress.md` is the owner's milestone feed, not a gate-tool transcript (BL-0014).** Mission Control's Summary tab renders this file verbatim (`readActivityLog`) — every entry appended by the engine, the supervisor or an agent MUST be a milestone: an FRD/WO built or changed, a decision taken, an item blocked needing the owner, a deviation from plan. **Never append a raw gate-tool exit line** (`**Biome:** limpio. Exit 0.`, `**tsc:** limpio. Exit 0.`, `**knip:** limpio. Exit 0.`, `**madge:** sin dependencias circulares. Exit 0.`, `**Vitest:** 327 ficheros… Exit 0.`, `**Smoke (Playwright):** 14/14 pasados. Exit 0.`, `**Visual (Playwright):** 14/14 baselines coincidentes. Exit 0.` or anything shaped like a `verify.sh` recap) — `verify.sh`'s per-tool results are evidence the reviewer/engine consume internally to decide PASS/FAIL, not owner narrative. When an FRD gate passes, write what it means ("FRD-05 Settings verified — WOs 01–04 built the preferences panel + persistence"), not the tool checklist that proved it. Full contract: `factory/standards/build-orchestration.md` §7.

## Decision points (escalation, visible in Mission Control)

When something unplanned appears: **first investigate** (delegate to `researcher`); if you can take the coherent decision yourself, do so and document it. **Only escalate genuinely human decisions** (product scope, irreversible, spending money, or what the registry marks human): note it in `.pandacorp/inbox/decisions.md` as `pending` (what's happening, options, **your recommendation**), notify the owner, and continue with independent FRDs. The owner answers with `/pandacorp:decide`.

**Closing out a decision — edit the ORIGINAL block in place, never just append (DR-069; owner incident, 2026-06-30).** When the build resolves a logged decision **autonomously mid-build** (a repair pass makes it moot, a later fix supersedes it, the blocking work order finishes another way — the owner-answered path runs through `/pandacorp:decide`), you MUST close it the same way the owner path does: edit that decision's OWN heading + `- **Estado:**` line to `RESUELTO: <what/why> (YYYY-MM-DD)` or `OBSOLETO: <what changed> (YYYY-MM-DD)`; a separate narrating entry is welcome as EXTRA context but never a substitute (Mission Control and `/pandacorp:decide` parse each block's OWN heading, so an untouched heading reads "pending" forever). The full shared protocol — RESUELTO vs OBSOLETO, closing a decision a newer sibling already resolved, the never-decide-obsolete-for-them gate — lives in `plugin/skills/decide/SKILL.md` step 4.

## Final hardening step — the audit moves INTO construction (DR-085, CABLED in the engine — BL-0012)

Construction's **last step**, once every FRD is `VERIFIED`, is the hardening pass that used to live in `/pandacorp:release`. **This is no longer prose — the ENGINE runs it** (`pandacorp-build.js`, the `Hardening` phase before close-out) and **`phase: release` is fail-closed on its evidence**: the close-out asserts a `docs/reviews/security-*.md` dated this run AND the `## Verification` section in `docs/analytics/events.md` exist before it may set `phase: release`; if either hardening stage fails, the engine keeps `phase: implementation`, files a needs-owner decision and notifies — it NEVER self-declares release on the FRD loop alone (the fail-safe close can't either):

1. **Security audit + fix** (two spawns, audit-then-fix — RFC-30 N4): essential web OWASP + **OWASP Top 10 for Agentic Applications** (ASI01–ASI10, DR-017) if the product has agents/LLMs with tools. First the **read-only `security-auditor`** agent audits and writes the evidence report `docs/reviews/security-<date>.md` (each finding + severity + remediation) — it never edits code (that independence is the point). Then a **Write/Edit-capable `implementer`** agent applies every Critical/high fix (TDD) and re-runs `verify.sh --since` until green, **before construction is declared complete** — never deferred to release. Evidence: `docs/reviews/security-<date>.md` (the same report, annotated fixed | accepted).
2. **Telemetry / metrics verification** (`analytics` agent, spawned by the engine): verify the events in `docs/analytics/events.md` actually fire in the critical flow (evidence, not "they should"). Evidence: the `## Verification <date>` section in `events.md`. The product is instrumented as part of the build (DR-085).
3. **Quality close-out**: the full suite + e2e green, lint + typecheck clean, the shell-presence gate green (the per-FRD gates already enforced correctness + shell), and — running here for the FIRST time (DR-106) — the whole-project **visual + responsive** gates (the per-FRD gate scopes its browser layer to smoke + shell, so the full visual/responsive suite runs once, here at close-out) + the cross-feature integration review. **README drift check (DR-112/DOC-3, advisory):** work orders can add env vars or change scripts mid-build — confirm the root README's "Getting started" commands and env-var pointer still match the current `package.json` scripts and `.env.example`; fix inline if they drifted. Never blocks the gate on its own.

Only when this hardening is green — evidence on disk, asserted by the close-out — is construction complete.

## When all are done
Full suite + e2e green **and the hardening evidence present (audited, instrumented, quality-gated — DR-085/BL-0012)**, then the engine's close-out sets `.pandacorp/status.yaml → phase: release`. (There is no `operation` phase — reaching `release` means the build is ready to be launched by `/pandacorp:release`, internal or external.) **Harvest the lessons now (DR-047) — a REQUIRED close-out step, not a suggestion; close-out is when they're freshest.** Three sub-steps, in order:
1. **Harvest**: run a `librarian` harvest of this project (drain `.pandacorp/run/lessons.md` + the build's capture points — reviewer findings seen ≥2×, fixed bugs, library verdicts chosen in the blueprint — into `factory/memory/` as evidence-anchored candidates, A.U.D.N.-deduped via `/pandacorp:memory harvest <project>`), so the NEXT build inherits what this one learned instead of relearning it.
2. **Measure retrieval**: run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/count-lesson-citations.sh" <project-dir> <factory-path>/factory/memory` — it greps the build's artifacts (blueprints, reviews, WOs, progress log) for `LESSON-NNNN` citations and deterministically updates each cited lesson's `applied_in`/`times_applied` (and auto-queues `promotion: proposed` at ≥3 distinct citing projects). Scripts measure retrieval, not agent self-report.
3. **Stamp it**: write `last_harvest: <ISO timestamp of now>` into `.pandacorp/status.yaml`. **A close-out without the stamp is an INCOMPLETE close-out** — do not report the build finished without it. The scheduled memory sweep treats a `phase: release` project with a missing/stale `last_harvest` as un-harvested and drains it as a backstop, so a skipped step is caught, not lost.

The periodic review sweep reconciles the harvested candidates and proposes promotions to the owner. This closes the self-learning loop at its highest-signal moment (the always-on capture is the supervisor's job during the run; this is the refine step). Summary to the owner + next step `/pandacorp:release` (the deploy/launch — internal or external).

## Rules
- Never advance with red tests. A WO that can't pass: the engine first attempts a **repair**; only if that fails = **freeze-on-red** (don't commit broken, leave HEAD at `last_green_sha`, mark `BLOCKED` + `blocked_reason` in the frontmatter, notify, continue with independent features). The build runs to completion; it stops only by budget/health or when something `needs-owner`.
- **State is the frontmatter** (`implementation_status`), never body prose or git (DR-050). `VERIFIED` is never rebuilt.
- **Never `git stash` to preserve in-flight work across a kill / relaunch / stop (DR-067).** The build is resumable from the frontmatter + commits, so killing or stopping a run discards only the uncommitted work between two safe points — the relaunch rebuilds it from `PLANNED`/`IN_PROGRESS` state, never re-doing `VERIFIED`. A `git stash` of in-flight work, popped later onto a tree that has moved on, **conflicts** (the MC Phase-2 incident). The only safe recovery from a dirty/conflicted tree is to **discard its uncommitted edits** — restore the project's own dirty paths to `HEAD`, never to `last_green_sha` (the pin is older than HEAD whenever `IN_REVIEW` work was committed after it, and a checkout of the pin also stages the reversal of those commits for the next commit to erase) — never a stash-pop. **Leave every stash untouched** (BL-0202: the stash list is repository-wide) and clean leftover temp `preview-wo*` pages — they're stale; the work is resumable.
- Quota limits: lower the mode (fewer parallel agents / cheaper models). Not a code error. In the fast lane a usage limit halts the run cleanly (`paused-infra`, §The fast lane): relaunch with the default lane once the window resets (`--resume <build_run_id>` when its lease went stale).
- If a work order reveals the blueprint/FRD was wrong, document the conflict, fix the source doc (ADR if architectural), then continue.
- **Don't trust the worker's honesty** (constitution §22): the `reviewer` re-verifies everything; the environment is fail-closed. Never relax verification because "the agent said it passed".
