---
name: change
description: The SINGLE front door to ask a Pandacorp project for ANY change — a new feature, an adjustment, or a bug. You describe it in plain language; the skill classifies it (feature/change vs bug vs milestone-scale) and gives it a class of service (urgent vs normal), then files it in the project's change queue (.pandacorp/inbox/changes/). It also derives the change's rigor level with a deterministic script; by default it stops at capture (`--queue` behaviour). On explicit `--now`, it goes on to IMPLEMENT and close a micro/normal change in the same turn, via a delegated subagent in its own worktree, the level's verify.sh gate, an independent reviewer, and a batch close-out — refusing itself (falling back to capture-only) whenever the change is critical, touches the floor, or a build is running. Runs INSIDE the project.

# /pandacorp:change

**The one command for "I want something changed or fixed."** You don't have to remember whether it's a feature or a bug — describe it, and `change` classifies it, gives it an **urgency class**, and drops it in the **change queue** `.pandacorp/inbox/changes/`. A running build **drains the queue at its next safe point**; if no build is running, `/pandacorp:implement` empties it when you run it. By default, that's where it stops: capture. For a small or medium change with no build running, you can also ask it to skip the wait and implement + close it in the same turn (**`--now`**, `## Fast path` below) — opt-in until the `## Dry run` canary has run green with D2 fixed (`references/now-mode.md`).

**Why this is safe (DR-069):** the **capture half never changed.** It still only **captures + classifies + writes one file**, it still **has NO build-detection logic**, and it still cannot mis-detect a running build and corrupt it. The queue is a durable folder; your change waits there safely until the build pulls it **at a safe point** (between features, never mid-feature) and integrates it through the same review/test gate as planned work. The fast path is a **second half bolted on after** the card is safely written: it reads build state and the rigor verdict **only to decide whether to do LESS**, its every failure mode lands back on capture-only, and it **refuses itself** on `critical`, on any floor signal, and on a live build. The engine stays the sole writer while it runs.

> **Preflight (DR-045) — is this a Pandacorp project?** This skill writes one file to `.pandacorp/inbox/` (capture only), so first confirm the Pandacorp marker: `.pandacorp/status.yaml` exists. If it's missing, STOP and tell the owner (in Spanish) that this folder isn't a factory project yet — `/pandacorp:adopt` brings an existing project in, `/pandacorp:spec` creates a new one. Then, if `overlay_version` in `.pandacorp/status.yaml` is behind the plugin's `OVERLAY_VERSION`, run `/pandacorp:upgrade` first (silent for compatible bumps, DR-048) — **but if a build is running (`running: true` + fresh `supervisor_heartbeat`) do NOT run `/pandacorp:upgrade` mid-build: it must never regenerate the engine/gates under a live build (its own active-build guard also refuses).** Capture only writes one file to the queue and is safe on an older overlay, so capture anyway — this gates only the optional upgrade side-step; capture itself stays build-detection-free (the DR-069 safety above).

`$ARGUMENTS` (or the conversation): what you want — e.g. `/pandacorp:change "the save button does nothing on Enter"` or `/pandacorp:change "add a CSV export to the orders table"`. Two flags: **`--now`** (explicit; eligible only for a micro/normal change with no build running) implements and closes it in this turn; **`--queue`**, the default, is capture-only, exactly as this skill behaved before the fast path existed.

## Steps

1. **Capture + classify the TYPE.** From the description decide:
   - **bug** (something is broken vs. what's expected) → capture the `bug`-flavored fields (steps · expected · actual · which screen/FRD).
   - **feature / change** (a new capability or an adjustment) → capture the `iterate`-flavored description (desired behavior + context; flag if it needs new design/visual).
   - **an answer to a question the build asked** → this is NOT a change → redirect to `/pandacorp:decide`.
   - **milestone-scale** (a large redesign, or a whole batch/package of changes that justifies its own mini-PRD — the AGENTS.md `new-version` criterion, not a single feature/adjustment) → this is NOT a queue card → go to **step 1b** (owner-gated handoff to the `new-version` engine).
   Ask the **minimum** to make it actionable; do NOT investigate, design, or fix here.
1b. **Milestone-scale → owner-gated handoff to `new-version` (NO queue card; capture-only boundary preserved, DR-069 §5).** A milestone is worked by the **`new-version`** engine (with its own mini-PRD), NOT drained from the change queue — the build's drain has no milestone branch, so a queued milestone card would be **dead-letter**. So `change` writes **nothing** to the queue here: it **explains to the owner (in Spanish)** that this is a milestone and **asks for their go** — e.g. *"Esto es un hito (un rediseño grande o un paquete de cambios con su propio mini-PRD), no un cambio de cola normal. Lo lleva el motor `new-version`. ¿Le doy paso ahora?"* **Only on the owner's explicit "sí" IN THIS SAME CONVERSATION** do you hand off — by running the internal engine `plugin/skills/new-version/SKILL.md` with the owner present (never via the queue, never unattended). If a build is running, tell the owner the milestone does **not** start mid-build: it begins after the build reaches a safe point (or the owner pauses it via `rethink_pending`), per **DR-069 §5** — `new-version` mutates docs and must never run concurrently with a live build. `change` itself still **edits no docs/code**: the handoff is the owner starting `new-version`, which runs as its own engine. If the owner declines or wants it smaller, fall back to the normal **feature/change** classification (a queue card).
2. **Assign the CLASS of service** (urgency — Kanban classes of service, DR-069):
   - **expedite** — urgent / it breaks something / blocks testing → the build jumps it to the front at the next safe point.
   - **standard** (default) — normal work, taken FIFO when the build reaches it.
   - (`intangible`/`fixed-date` exist for completeness but are rarely needed — default to `standard` unless the owner signals urgency.)
   Propose the class; confirm with the owner only if it's ambiguous or `expedite`.
3. **Flag the cost.** If the change clearly **rebuilds already-`VERIFIED` work** (e.g. "redo screen X completely"), say so in the body so the owner knows — and a big/structural/fundamental change is captured but marked so the build **stops and guides the owner** before doing it (it never silently rebuilds half the app).
3b. **Flag a rule supersession (DR-116).** If the request **changes an existing rule/contract** — not just adds behavior, but replaces a stated rule (a limit, a default, an acceptance criterion, a data-model fact) — note **what old claim it supersedes** in the change-request body (`supersedes:` one line). This is only a DECLARATION here; `iterate` (when the build integrates it) runs the supersession-completeness check so the old claim doesn't survive in another doc. Adding-only changes carry no `supersedes:` — don't invent one.
4. **Write the change-request** to `.pandacorp/inbox/changes/<slug>.md` (following `${CLAUDE_PLUGIN_ROOT}/templates/docs/change-request-template.md`; slug in English; **body in Spanish** — this is the gitignored owner layer):
   - frontmatter (machine, English-stable): `type: bug|feature|change`, `class: expedite|standard`, **`status: draft | ready`** (DR-069), `date`, `frd` (affected feature/screen if known), `rebuilds_verified: true|false`, `rigor` + `rigor_reasons` (step 4b), `depends_on` (optional).
   - **`status` — READY vs DRAFT (the build gate, DR-069):** **`ready`** = the description is complete enough to action → the build (`implement`) **drains and builds it**. **`draft`** = captured for visibility but the owner is **still working out the details / it depends on something not done yet** → the build **SKIPS it** until the owner flips it to `ready`. Default to `ready` for a clear, actionable request; use `draft` if the owner says "just note it, it's not ready," if key info is missing, if it needs a design pass first, or if it's **infra/deployment** (not code the build implements — that's a manual/`release` task). The owner sets only `draft`/`ready`; **the CLOSER manages three states you never write at capture time**: `building` (engine-only: the change is in flight — its FRDs are being built; the safe-point won't re-drain it), `closing` (written by `/pandacorp:sync --close-out` with `implemented_sha` + `closing_at` the instant a close-out starts, so an interrupted one stays visible; `doc-lint.sh` reds it past 48h) and `done` (its affected FRDs all VERIFIED → moved to `changes/done/`), the durable cross-run archival (DR-069 §7 / WS-A/D1).
   - body (**español**): para un bug — *pasos · esperado · actual*; para feature/cambio — *qué se quiere · contexto · (si toca diseño) "necesita pase de `/design`"*.
   - Append a row to the queue index `.pandacorp/inbox/changes/README.md` (following `${CLAUDE_PLUGIN_ROOT}/templates/docs/changes-readme-template.md`; title · type · class · status).
4b. **Derive the RIGOR (never ask it).** `class` decides WHEN a change is picked up; `rigor` decides HOW MUCH evidence it must collect. It is computed by a deterministic script over the paths the change will plausibly touch (enumerate them yourself, in this session, from the description plus a bounded look at the tree): `bash "${CLAUDE_PLUGIN_ROOT}/scripts/classify-change.sh" --repo . --files "<comma list>" --card <card>`. Copy `rigor` and the signals behind it into the card's `rigor:` / `rigor_reasons:`, and show the owner ONE line: *"clasificado como <nivel> (provisional): <razones>"*. **You may only ESCALATE the verdict**, stating why in `rigor_reasons`; nothing may lower it. This pass is PROVISIONAL by construction: `--files` carries no diff body, so it can never certify `micro`, and the definitive level is recomputed on the real diff at close-out. Detail: `references/now-mode.md` §1.
5. **Branch: capture-only, or the fast path.** By default (no flag, or **`--queue`**), stop here and **confirm** to the owner (Spanish): "Anotado en la cola como **[tipo · clase · rigor]**. El build lo toma en su próximo safe point. Si no hay build corriendo, corre `/pandacorp:implement` y lo recoge." Only on an **explicit `--now`**, and only when no valve in `## Fast path` fires, continue into it and implement now.

## Fast path: `--now` (proposal 37 §A.8; operative detail in `references/now-mode.md`)

**Opt-in, on explicit `--now`, for a micro/normal change written `status: ready`, with no build running.** (The default stays capture, `--queue`, until the `## Dry run` canary below has run green with defect D2 fixed — see that section for the exact flip criterion.) The card is already written, so every exit below is safe: the worst outcome is the queue behaviour this skill always had. **A `status: draft` card never enters the fast path** (DR-069: `draft` means the owner is still working it out, it needs a design pass, or it is not code the build implements); capture it and stop, exactly as `--queue` does.

**A. Three valves, in this order. Each one ends the turn with the card captured and nothing else written.**
   1. **A build is active** → capture only. Read liveness through the one helper, never by hand-parsing `status.yaml`: `bash "${CLAUDE_PLUGIN_ROOT}/scripts/check-build-liveness.sh" .pandacorp/status.yaml` (`RUNNING`), or a lease with `fresh: true` from `pandacorp-build-state.mjs status`. Tell the owner the build drains it at its next safe point. (`STALE` is not a live build and is not yours to clear: proceed, and leave the reset to `/pandacorp:implement`.)
   2. **`rigor: critical`, or any `floor_hits[]` entry at `level: critical`** → capture only, `class: expedite` if the owner signalled urgency. Name the exact signal verbatim (auth, money, PII, persistence, irreversible, secrets/CI, the oracles, the factory's machinery) and offer `/pandacorp:implement frds=<frd>` or a bare `/pandacorp:implement`. **The fast path may never touch the floor.** Pass `--wo <path>` when a target work order is known, so S12 can see it; and because S12 reads only a WO, **also treat `difficulty: high` or `reopen_count >= 1` written on the CARD as `critical` yourself** (the classifier does not read those from a card, so this is the only place that check exists).
   3. **The classifier failed** (non-zero exit, no parsable verdict) → treat as `critical` and take valve 2. A broken classifier must never be why a change ran cheap.

**B. Implement by DELEGATION, never in the owner's session** (a turn here carries the whole accumulated context; a fresh subagent starts clean). A `pandacorp:implementer` (or `frontend-dev`/`backend-dev` when the artifacts say so), **always on the model its agent definition pins, which is `sonnet` for all three (CONV-12's floor for real work). Never escalate the implementer to opus on this path**: the reviewer is opus, so an opus implementer would break DR-015 (judge is a different agent AND a different model). Work that genuinely needs an opus builder is `difficulty: high` work, which valve 2 already sends to `/pandacorp:implement`. In **its own worktree** (DR-096: `EnterWorktree`, else `git worktree add` + `bash .pandacorp/worktree-bootstrap.sh`), with a **self-contained brief** (PROMPT-8): the card and its acceptance criteria verbatim, the probable-paths list, a **context budget of ~40k tokens** (read only what the artifacts require; `design-tokens.json` only if it touches UI), TDD, the level's gate command (`verify.sh --since <last_green_sha> --report-all`; `--only`/`--files` only inside its own retry loop, because a `partial` scope certifies nothing), `git add` of its own files only, and an explicit output contract (files touched · commit sha · the `gate-report.json` path with its `green` and `scope`).

**C. Judge by level.** **L0 `micro`: no LLM reviewer.** The oracle is the canonical `verify.sh`, which the implementer did not write, and the verdict is a `green: true` report whose `scope` is `since` or `full`. **L1 `normal`: one `pandacorp:reviewer` on opus**, a different agent AND a different model from the implementer, which is **DR-015 met explicitly**. It is fed pre-digested evidence (diff + `gate-report.json` + the acceptance criteria) so it does not have to go exploring, and is capped at ~15 exploration calls and ≤3 adversarial tests, returning structured findings. **It still RE-RUNS the gate itself** rather than trusting the implementer's report (`plugin/agents/reviewer.md` §1, and "generator ≠ verifier" in `quality-and-testing.md`): the cap buys back exploration turns, never the independent oracle. This is a per-change invocation of an agent whose standing contract is per-FRD; extending `reviewer.md` itself is a separate, frontmatter-level change (PROMPT-5). **A red blocks at every level.** Blocking findings go back to the same implementer for **at most 2 repair cycles**; still red means an honest hand-back (DR-099): work preserved on its branch, and the owner told in chat, in this turn, what is blocked and why.

**D. Reclassify on the REAL diff, then close out.** `classify-change.sh --repo <worktree> --range <base>..<head> --card "$PROJECT_ROOT/.pandacorp/inbox/changes/<slug>.md"` is the only classification that certifies anything — `--repo`/`--range` point at the implementer's WORKTREE (S17/madge only trusts the on-disk import graph when the classifier's `HEAD` is the branch tip, `isHeadRange`), while `--card` stays on `$PROJECT_ROOT`, the original checkout captured in §1 of `now-mode.md`: `.pandacorp/inbox/` is gitignored and a fresh worktree never materializes it, so a `--card` path resolved inside the worktree fails closed to `critical` (BL-0162; detail in `references/now-mode.md` §5). **Risen to `critical` → do NOT land it**: hand back with the firing signal and offer `/pandacorp:implement`. Still micro/normal → `/pandacorp:sync --close-out <slug>` stamps `status: closing` + `implemented_sha` + `closing_at` first (so an interrupted close-out stays visible), then writes the level's artifacts, one commit and the card to `done/` with `shipped_sha`. **Close-out is also the single writer of the work order's `implementation_status`** (DR-097 says the gate's verdict is recorded, DR-115 says one fact has one writer): do not set `VERIFIED` yourself. Land with `bash .pandacorp/merge-queue.sh` (product projects) or a direct merge to `main` (the factory and Mission Control, which have no merge queue), then `ExitWorktree`. A landing that hands back is said in chat immediately, never worked around. Close with one Spanish line: *"hecho · nivel · gate · commit · card archivada"*.

## Rules

- **The fast path is a second half, never a softening.** Capture still comes first and still stands alone; `rigor` decides how much EVIDENCE a change collects and **never** whether a red gate blocks. Every valve, every failure and every refusal lands back on capture-only, which is this skill's original behaviour. Detail: `references/now-mode.md`.
- **The QUEUED path does not integrate docs or build.** Capture + classify + queue, nothing else (`--queue`, and every fast-path valve). The build (`implement`) drains the queue **at a safe point** and runs the integration — delegating to the **`iterate`** logic (a feature/change → FRD/work-orders/blueprint, calling `work-orders`/`design` as needed) or the **`bug`** logic (a bug → regression test then fix) — and then the **FRD review/test gate**. So a queued change passes the **same quality gate** as planned work and is never edited into the build's docs concurrently (DR-067/069).
- **One door for the owner; `bug` and `iterate` are the internal engines.** You classify internally so the owner only remembers `/change`. `/pandacorp:bug` and `/pandacorp:iterate` are the **internal engines** that `change` and the build invoke for the bug/feature cases — both are hidden from the owner's slash menu (`user-invocable: false`); neither is an owner command. The owner always reaches them through this single front door.
- **Only `ready` items are built (DR-069).** The operative rule is in step 4: the build drains `status: ready` (expedite first, then standard FIFO) and skips `status: draft`; the owner promotes a `draft` by flipping it to `ready`.
- **On completion, the closer ARCHIVES — never hand-deletes (DR-069).** On the queued path the closer is the build; on the fast path it is `/pandacorp:sync --close-out`, under this identical rule. When a change lands, the closer (not you, mid-flight) verifies its durable record exists **at the level's bar** (proposal 37 §A.6 operationalizes the "don't record trivial changes" exception with a deterministic criterion instead of in-the-moment judgment): `normal` and `critical` require the canonical doc touched **and** a `docs/decision-log.md` entry referencing it; `micro` requires the card in `done/` with `shipped_sha` plus the `progress.md` line, and a decision-log entry **whenever `supersedes:` is non-empty**. The level never decides WHETHER a change is recorded, only how much. It stamps `status: done` + `shipped_sha` + `shipped_at`, and **moves the file to `changes/done/`** (a move, never an `rm` — the folder is gitignored, so a delete is irreversible). The active `changes/` stays **pending-only** (your clean queue); the owner-language trail survives in `done/`. Any later cleanup of `done/` is a separate, owner-gated, reversible prune — never automatic.
- Keep scope bounded to what was asked (DR-012). Conventional commits in English; the change-request body in Spanish.
