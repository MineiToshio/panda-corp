# /pandacorp:upgrade

Brings this project's Pandacorp overlay up to the factory's current version. The `/pandacorp:*` skills always run against the **latest** plugin, so a project born on an older overlay can drift; this closes the gap. Runs IN the project. It touches only the overlay/integration layer — never product code or `docs/`.

## Active-build guard (HARD, before any mutation)

Resolve the active plugin root (`CLAUDE_PLUGIN_ROOT` in Claude Code; the factory/plugin path in `.pandacorp/guide.md` under other runtimes). Run BOTH read-only checks from the project:

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/pandacorp-build.mjs" status --project .
bash "${CLAUDE_PLUGIN_ROOT}/scripts/check-build-liveness.sh" .pandacorp/status.yaml
```

Parse the top-level CLI JSON: a live `lease.live` or an armed `drive.armed` means **ABORT**, even if the YAML says otherwise. The helper's `RUNNING` (exit 1, including an unreadable status or malformed existing lease) also means **ABORT**. A failed CLI, invalid JSON, reported `gaps`, or any inconclusive ownership signal blocks the upgrade; do not clear a lease or stop a run to get past this guard. Only a successful status without live ownership together with `NOT_RUNNING` (exit 0) or `STALE` (exit 2) permits proceeding. Recheck immediately before changing managed files.

Tell the owner in Spanish that the upgrade is deferred until the build stops. Do not regenerate instructions, gates or hooks, remove retired files, stamp a version or commit under a live build. The calling skill may continue only its already-authorized work on the existing overlay; this refusal never authorizes launching another build.

**Never mix plugin versions on one project (owner decision 6).** After `claude plugin update pandacorp@panda-corp`, restart or close **every** session working on that project before continuing. A new session must resolve the same installed plugin version and root; do not combine an old loaded skill with new scripts or templates. Apply the same restart/close rule after updating the plugin in another runtime.

## How it decides

- **Project version**: `overlay_version` in `.pandacorp/status.yaml`. A pre-6.0.0 project has no `.pandacorp/` and no `overlay_version` → treat it as the oldest (it needs the overlay-relocation migration). A pre-DR-049 project (overlay ≥ 6.0.0 but with the old **by-type** `docs/` layout — flat `docs/frds/frd-NN.md`, global `docs/blueprint.md`, global `docs/work-orders/`, `docs/prd.md` at the root of `docs/`) additionally needs the **feature-centric docs migration** (step 2b).
- **Target version**: `${CLAUDE_PLUGIN_ROOT}/templates/OVERLAY_VERSION`.
- **In sync** (`overlay_version` == target) → say so and do nothing (idempotent).
- **Behind** → upgrade. **Compatible** bumps (same MAJOR) apply **silently** (DR-048) and you only see the commit; a **MAJOR** jump (breaking — a moved/renamed field or path) is **announced first** with the diff, never applied blind.

## Steps

1. **Detect the gap.** Read the project's `overlay_version` (absent = pre-6.0.0 layout) and the plugin's `OVERLAY_VERSION`. If in sync, stop ("already on overlay X").

2. **Overlay-relocation migration (pre-6.0.0 → 6.0.0+).** If the project still has the OLD layout, move the integration layer into `.pandacorp/` (use `git mv` where tracked to preserve history):
   - `docs/status.yaml` → `.pandacorp/status.yaml`
   - `docs/iteration.md` → `.pandacorp/comms/iteration.md`; `docs/summary.md` → `.pandacorp/comms/summary.md`; `docs/progress.md` → `.pandacorp/comms/progress.md`; `docs/activity.md` → `.pandacorp/comms/activity.md`
   - `docs/decisions.md` → `.pandacorp/inbox/decisions.md`; `docs/bugs/` → `.pandacorp/inbox/changes/` (each old bug file becomes a `type: bug` item in the unified queue — DR-069; an old `.pandacorp/inbox/bugs/` from a 6.x overlay migrates the same way)
   - `docs/idea-origin.md` → `.pandacorp/idea-origin.md`
   - **STAY in `docs/` (product)**: `decision-log.md`, `prd.md`, `frds/`, `blueprint.md`, `adr/`, `work-orders/`, `design/`, `reviews/`, `product-research.md` (the feature-centric migration in step 2b then reshapes these).
   - Update the project's `.gitignore`: add `.pandacorp/comms/`, `.pandacorp/inbox/`, `.pandacorp/run/`; drop the old `docs/{summary,progress,decisions,iteration,activity}.md` ignores.

2b. **Feature-centric docs migration (pre-DR-049 by-type → feature-centric).** If the project still has the old by-type `docs/` shape, reshape it into the feature-centric layout (DR-049 — see `factory/standards/structure.md`). Use `git mv` where tracked; preserve the stable IDs (`REQ-NN-MMM`, `AC-NN-MMM.K`, `WO-NN-MMM`) — numbers never change, only their location:
   - **Product layer**: `docs/prd.md` → `docs/product/prd.md`; `docs/product-research.md` → `docs/product/research.md`. Add a living **feature-landscape** table to `prd.md` if absent (one row per FRD module).
   - **FRD modules**: each flat `docs/frds/frd-NN-<slug>.md` → its own module folder `docs/frds/frd-NN-<slug>/frd.md`. Per-feature design (if the project had a separate per-feature FDD) → `frd-NN-<slug>/fdd.md`; feature mocks → `frd-NN-<slug>/mocks/`. The global design system (`docs/design/`) stays GLOBAL — never split it per feature.
   - **Blueprint split**: the global `docs/blueprint.md` is split — the **platform** parts (stack, data model, deploy, cross-cutting, service boundaries) → `docs/product/architecture.md`; each **per-feature** implementation section → that feature's `docs/frds/frd-NN-<slug>/blueprint.md` (referencing `product/architecture.md`). When the per-feature split isn't cleanly separable, keep the bulk in `architecture.md` and add thin per-feature `blueprint.md` files that point to it; don't fabricate detail.
   - **Work orders**: distribute the global `docs/work-orders/wo-NN-MMM-*.md` into their FRD's folder by their `NN` prefix → `docs/frds/frd-NN-<slug>/work-orders/`, each with a per-FRD `work-orders/README.md` (intra-feature order + parallelism). Cross-feature order continues to come from each WO's `Dependencies`.
   - **Unchanged**: `docs/design/` (the global PDD), `docs/adr/`, `docs/analytics/events.md`, `docs/decision-log.md`, `docs/reviews/` — these stay where they are.
   - Fix internal cross-links broken by the moves (PRD↔FRD, WO→FRD/blueprint references) so they still resolve.

A NEW project, by contrast, is born `responsive` (the status.yaml template default) — only the retrofit is conservative.

3a. **Prove the gates still BITE after re-syncing them (DR-079).** Once the gate-config conformance (step 3) has regenerated `verify.sh` + `canary.sh` + the e2e files, run `.pandacorp/verify.sh --canary` — `canary.sh` GENERATES a deliberately-broken input per gate (no broken files kept in the repo), pushes each through its gate, and REDs if any gate that should reject its broken input stays green (a rotted gate: a renamed spec, a disabled rule, a swallowed exit code). It canaries EVERY fail-closed gate: biome (`--error-on-warnings`), the test-placement structure guard, the DR-100 readiness gate, tsc (strict types, via an isolated temp tsconfig), madge (circular deps), vitest (a failing test), knip (an orphan file), and Playwright spec DISCOVERY (proves the config still finds smoke/visual/responsive/shell so the e2e layer can't pass vacuously — a fast `--list`, no browser run). NOT canaried, by design: a full Playwright browser run (discovery + the fail-closed missing-harness checks + conformance cover its rot modes) and `doc-lint.sh` (advisory, never reds). **A canary failure here is BLOCKING for the upgrade** — a rotted gate means the project's enforcement is fiction: fix the gate (or back-port the genuine fix, DR-076) and re-run before stamping `overlay_version`; never stamp an upgrade "done" over a red canary. (A project with no `canary.sh` can no longer occur post-conformance — the same pass installs it; if the install itself failed, that IS the blocking finding.) Conformance proves the gate FILES match the template (DR-059/076); the canary proves they still FUNCTIONALLY reject. The project must then also still PASS the gate for real (step 3b).

3b. **Post-conformance PROJECT gate run (DR-076 amendment, BL-0003) — fail loud, never leave a broken baseline.** After the conformance overwrite has re-synced the gate config (step 3) AND the `--canary` proved the gates still bite (step 3a), run the FULL project gate ON THE PROJECT: `.pandacorp/verify.sh` (a full baseline run, NOT `--since` — the config the overwrite just touched is untracked-by-diff at the FRD level, exactly the blind spot that hid the personal-page-v2 red-lock; the per-FRD `--since` gate lints only changed files, so a red-locking `biome.json` slips through until pass-2). If `verify.sh` is not runnable standalone, at minimum run `biome check . --error-on-warnings` + `knip` + `tsc --noEmit`. **If the freshly-synced config RED-LOCKS the gate, STOP — this is BLOCKING for the upgrade:** do NOT stamp `overlay_version`, do NOT commit. Report the red loudly and either (a) back-port the project's newer config to the template (the "project newer than template" case the detector in step 3 should already have caught — the conformance overwrite downgraded a correct config), or (b) fix the template if the template itself is genuinely broken; then re-run conformance + this gate until green. The DR-079 canary proves the gates FUNCTIONALLY reject a broken fixture; it does NOT prove the PROJECT still passes after the overwrite — this run is the missing check that would have caught the silent downgrade before the next build discovered a dead gate (`builtFrds:[]`, `blockedReasons:{baseline:error}`). Skip only when the project has no `verify.sh` at all (a pre-DR-059 project that just had it installed for the first time still runs it here — the install is the point).

4. **Bump + record.** Set `overlay_version` to the target in `.pandacorp/status.yaml`. Add a `docs/decision-log.md` entry: "Pandacorp overlay upgraded `<old>` → `<new>`"; if step 2b ran, note the feature-centric docs migration (DR-049) and that it was a pure relocation (IDs preserved, no behavior changed); if the gate-config conformance check (DR-059) regenerated `verify.sh`/`biome.json`/`knip.json`, note which drifted and that enforcement was re-aligned to the standard; if the toolchain check installed missing devDependencies/scripts or fixed `tsconfig`, note that too (the gate is now runnable cold).


   inside the factory), it stages only the named regular managed files even if the parent repository
   ignores `.pandacorp/`; it never stages `run/`, `comms/`, `inbox/`, accounts, secrets, caches, identities,
   installed hooks or unknown files. It refuses symlink machinery. See `plugin/docs/nested-projects.md`
   for the exact inventory. Stage the other changed integration files by their explicit paths; never
   `git add -f .pandacorp/` or broad repository staging in a shared factory checkout. Existing tracked
   owner-state files require a separate index cleanup; ignore rules do not untrack them.

   **Commit on its own**: `chore: upgrade pandacorp overlay <old> → <new>` (moved files + machinery + managed layer + any DR-049 docs relocation from step 2b). Do NOT mix product *behavior* changes into this commit — the docs migration is a structural move, not a content rewrite.

6. **Report** (in Spanish): what moved, what was regenerated, and the new version. If a MAJOR jump required a manual decision, surface it explicitly.

## Rules
- **Compatible (same MAJOR) = silent** (DR-048): apply and commit without interrupting; the owner sees it via the commit. **MAJOR = announce** the breaking parts + diff before applying.
- **Never clobber the owner's content**: managed files (`guide.md`, `README.md`, machinery) regenerate whole; `AGENTS.md` merges by managed section, the owner's notes stay, and `CLAUDE.md` stays the one-line shim.
- Touch only the overlay/integration layer — never product **code**, and never rewrite the **content** of product docs. The one exception is the DR-049 **feature-centric docs migration** (step 2b): a one-time structural *relocation* of `docs/` files (moves + link fixes, IDs preserved), never a content rewrite. A MAJOR overlay jump that carries this migration is announced first like any breaking change.
- **Gate config is conformance-checked, not merged (DR-059)** — canonical files overwritten from the template on any drift; `e2e/routes.ts`/`_target.ts`/`shell.ts` are PER-PROJECT and NEVER byte-diffed. Full set, downgrade detector, back-fill exceptions: **step 3**.
- **Canonical gate files are edited at the SOURCE, never in-place (DR-076)** — a fix made directly in a project's canonical gate file is **silently reverted on the next `/upgrade`** and leaves the template stale for everyone; make it in `plugin/templates/stack-<chosen>/` and back-port in the SAME change (a project-specific exception goes in a SEPARATE never-overwritten file; the `remind-backport-gate-config.sh` hook nudges this). The overwrite is unconditional; the `detect-gate-config-newer.sh` back-port-FIRST guard for a project legitimately ahead of the template is in **step 3**.
- **Conformance covers the toolchain, not just the config (DR-059)** — the check also reconciles the required devDependencies, scripts and a strict `tsconfig` so the fail-closed gate is runnable cold; exact set in **step 3**.
- **Prove the gates still BITE after re-syncing them (DR-079)** — operative in **step 3a**: `.pandacorp/verify.sh --canary` after conformance; a red canary is **BLOCKING** (never stamp `overlay_version` over a rotted gate).
- **Prove the PROJECT still passes after re-syncing (DR-076 amendment, BL-0003)** — separate from the canary; operative in **step 3b**: a full `.pandacorp/verify.sh` baseline (never `--since`) after conformance + canary; a red baseline is **BLOCKING** (back-port the project's newer config, never stamp over a red-locked gate).
- Idempotent: re-running when already in sync is a no-op.
