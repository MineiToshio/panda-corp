# External services and accounts

- Read the factory provider catalog and private account directory before choosing/provisioning a service; project associations live in `.pandacorp/accounts/services.yaml`. No personal identity or credentials in committed recipes. Account metadata stores references, never passwords/tokens. GitHub remains standard infrastructure outside service choices.
- Only current-version approved services get SDKs, keys, required env validation or work orders. Always resolve PostHog, Sentry, multilingual i18n, SEO and mailing-list needs independently. Kit is off by default; deferred/excluded is not a future stub.
- Reuse authorized accounts. Use exact `resource_slug` (for example `funko-tracker`) and default `<slug>.pandatrack.app`. Preserve existing names/resources; no automatic migration. Vercel hosts new web apps; one Neon project per app, dev/prod branches; pooled/direct URLs follow the framework contract.
- When R2 is needed, private `<slug>-dev` / `<slug>-prod` buckets use the same adapter against real R2 locally and in prod, different scoped credentials/config. No routine staging or custom MVP database backups to R2.
- Google OAuth defaults to shared PandaTrack project, one client per app shared across approved dev/prod callback origins. Reuse shared Resend domain with app/env scoped key where supported and hello sender with app display/subject context. Shared ImprovMX inbox needs plus-address/subject context to identify an app; generic mail may be unidentifiable.
- API/CLI first with verified identity and operation-specific scope; browser session does not prove token authorization. Reconcile stored IDs before create/retry. Record dated quotas and shared consumption; no account/organization proliferation to evade fees. Account creation/spending/deletion/production retain human gates.
- Record independent `detected`, `researched`, `account_verified`, `recipe_tested`, `reusable` evidence, never infer tested automation from documentation. New providers require approved scope, public recipe and private/project references before adoption.
- Preflight inventories only. After scope and the consumer contract are final, architecture fills every obtainable authorized provider value and locally generated app secret; a map alone is incomplete. Contract: name, purpose, origin, environment, exact web/worker/migration/local/CI destination, installed or concrete current-version WO consumer, required-now flag, secret reference and per-destination pending/generated/configured/verified/not_applicable status. Planned consumers cannot claim runtime verification. No speculative secrets; cryptographic app secrets use consumer-specific formats, distinct per purpose/environment except a documented shared protocol or the approved per-app Google OAuth client across environments.
- Exactly three root dotenv files: tracked placeholder-only `.env.example`, gitignored/untracked mode-600 `.env.local` (development) and `.env.production` (production handoff). Group by service within labelled destination blocks and identify app-generated secrets. Local-only dev/test/oracle/smoke/tooling entries are last in the guide/development file, never in production. Production includes only approved needed consumer entries. Separate roles/environments through aliases and explicit destination selection/export under real runtime names; never duplicate keys, inject the whole bundle, merge differently privileged credentials or generate extra per-worker/migration/tooling files. Verify actual loader precedence and no dev/other-role fallback with synthetic fixtures; missing bindings remain pending. Preserve existing values without rotation, inventory/reconcile legacy files before retirement and never mass-rewrite existing private files on upgrade. Refuse unsafe paths/concurrent edits; private temporary files, atomic writes, no secret output. Ignored files do not merge; deliver under main-checkout single-writer ownership, never copy production secrets through bootstrap. Provider-admin tokens stay outside runtime.
- Migration credentials, only when consumed: put them below the final local/operator-only separator in `.env.local` and `.env.example`; retain a separate production-migration operator block in `.env.production`. Comments say the command runs from the owner's Mac, which dev/prod database it targets, and which migration CLI reads the connection. Never upload it to Vercel/Modal runtime. A locally executed production migration still needs its production-target connection; do not classify that as unused local tooling. No new files, automatic migration execution or relaxation of production gates.
- Record value-free delivery/evidence and exact pending actor/actions in protected `.pandacorp/comms/entrega-entornos.md` (Spanish, gitignored, mode 600); independent review checks coverage/path/permissions/preservation and environment/target separation. Missing provider access stays pending. Configured files do not prove connectivity, execution, host configuration or production readiness. Procedure: architecture `references/environment-delivery.md`. Never put secrets in account catalogs, logs or examples.
