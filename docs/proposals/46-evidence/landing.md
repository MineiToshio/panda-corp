## 2. Who held the verification lock, and why FIFO did not help

**Attribution: the approval turn's light Stop hook, high confidence.** C:2084 has the verifier's owner PID and checkout path. C:2055–2058 ties this same session's Stop invocation to the overlapping interval, including the exact light command and completion time. D:3520 places a 13.654 s light green in that checkout. The earlier Stop at 19:49:03 had already finished. The worker's earlier checks ended before approval, and the two visible queue calls are the failed and successful ones above. No separate background `verify.sh` launch is present in the relevant tool calls. The Stop telemetry schema records project basename, scope, verdict and duration. It omits PID and parent identity, so the PID-to-hook link is a timeline and checkout inference. [C:2016–2048,2055–2058,2084,2097–2098; D:3513–3523; Factory/plugin/scripts/verify-before-stop.sh:228–248]

Three mechanisms matter here.

- **Repository FIFO.** The ticket and owned merge lock serialize rebase and main writes. `with-merge-lock.sh` sources the same library for direct writers. It does not run the Stop verifier. Both calls had position 1 and zero recorded queue-lock wait. Proposal 43's FIFO language is for waiters on the **repository merge lock**, and its two-session example is two landing invocations. The heavy-slot cap is a distinct bounded poll. Proposal 43 contains no explicit FIFO or adoption contract for a verifier already running in one checkout. [F/MQ:125–149,628–629; F/.pandacorp/with-merge-lock.sh:2–8,27–29; FQ:156–157,167–168; Factory/docs/proposals/43-done-means-queue-green.md:120–125,154–155,190–192,290–291; R:560–564,978–982]
- **Host heavy-job slots.** The queue acquires a slot only for the full path, passes its token down, and releases it after the verifier result. A standalone full verification takes or inherits a slot. A `--light` run avoids heavy-slot admission. The shell and engine use the shared host directory and ownership protocol. The observed acquisition of slot 0 and wait of zero make heavy-slot scarcity irrelevant to this collision. Funko's separate machine test lease can also delay browser work after admission. Its `lease-wait.json` existed in the worktree during the retry, but no evidence links it to the first rejection. [F/MQ:459–474,579–604,825–855; F/verify:442–480,556–605,963–972; Factory/plugin/runtime/build/admission/hostSlots.mjs:76–106,113–124; F/scripts/test/gateLease.mjs:159–195; FQ:161–164,172]
- **Physical-checkout verification lock.** `verify.sh` takes kernel `LOCK_EX | LOCK_NB` on `.pandacorp/run/verify.lock` before its own report/output changes, even in light mode. It writes PID/path into the existing inode, inherits the descriptor across children, and returns **75** immediately on contention. The file can remain after release. The queue deliberately maps 75 to **14** and skips report archival, reusing the pre-existing port-busy code (the header only documents that original meaning). Its cleanup releases the slot and merge lock and may bootstrap afterwards. The Stop hook reverses that relationship if it loses the same race, converting 75 into exit 2 and requesting another turn. Separate from this particular collision, the queue currently rebases, prepares inputs and can clear gate outputs/record metadata **before** the verifier's lock is acquired. Move this boundary earlier when fixing admission. [F/verify:50–76,122–130; F/MQ:10–21,614–625,676–775,830–859; Factory/plugin/scripts/verify-before-stop.sh:228–253; R:934–938]

The incident used the queue directly. The implement CLI would currently collapse any queue exit 14, including this verifier collision, into a successful-envelope `nothing_to_land` with reason `port_busy`. That misleading mapping is a separate reason to carry typed contention into the CLI. [Factory/plugin/runtime/build/land/batch.mjs:15–27; Factory/plugin/runtime/build/land/harvest.mjs:284–314]
