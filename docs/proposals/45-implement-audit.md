## Terms used

- **Work order (WO):** a product task with scope, dependencies and acceptance criteria. A **feature requirements document (FRD)** defines the behavior of a feature. A **change card** records the requested scope and references its governing documents.
- **Builder:** the agent that edits the product. A **unit** is an execution assigned by the engine. A **worktree** is a separate checkout. A **lease** records who owns a run and a **checkpoint** is a saved state from which work can continue.
- **Gate:** a scripted verification decision. **G1** checks a submitted unit before it enters the integration branch, **G2** checks the integrated feature, and **G3** is the queue’s final verification. The **Stop hook** can separately check changes at the end of a Claude turn.
- **Oracle:** the expected behavior and independent check used to judge a candidate. **Fail-first** means observing a regression assertion fail against the faulty baseline using functioning setup. **Independent review** uses a fresh qualified context and verifies the actual candidate.
- **Candidate:** an identifiable revision ready for review. The **queue** rebases onto main and certifies the resulting tree with the full check or a compatible existing **stamp**, which records proof for that exact tree and inputs. A **launched project** requires the owner’s explicit order for landing. Certification, local integration, confirmed push and observed deployment are distinct.
- **Shadow comparison:** an experiment in isolated copies with no authority to publish or modify live records. **Direct session:** one agent implementing the same scope without the implementation scheduler, with the comparison’s required review, state and final proof supplied and charged to that route.

## Are the prompts badly made?

The worker instructions mix a legitimate proof contract with instructions the executor could own. The archived brief prescribes “Run, in this order, one heavy tool at a time, at most 3 fix cycles” and “Record each command's exit code and the output tail in the report.” It asks for identical schema-valid JSON in a file and a final response. The implementer role says “Mandatory checklist per work order (in order, without skipping steps)” yet has an override for v2 tests-first. The reviewer’s older instructions tell it to update status and commit while the v2 section reserves those operations for the CLI. Scoped specialists are pointed to phase-wide roles with exceptions in the brief. A builder has little discretion when the runtime’s literal allowlist excludes an adjacent file. In the census a mismatch at a shared roster boundary exposed this fence. [Exact instructions and report fields](45-evidence/anatomy.md#2-what-the-worker-receives) · [Collisions and historical purpose](45-evidence/prompts.md#what-the-agent-sees-and-where-instructions-collide)

Some instructions protect a demonstrated need. Independent review caught real issues. A fail-first regression distinguishes a behavior defect from an import or setup error. Worktree, private test data, server ownership, exact review pinning and release permissions protect concurrent or consequential work. A prior reviewer interrupted host-wide servers. The freer-prose hypothesis is plausible for a correctly running builder choosing routine edits and making sense of handoffs. The quoted marker and unsupported report enum are concrete **ESTIMATED** candidates for wording changes. Their prevention is unproven, as are indirect effects elsewhere. A pre-model schema refusal, missing route types, stale scheduler state and a wrong checkout need mechanical fixes or a different execution path. The proposed copy leads with the outcome and authorizes routine decisions, while preserving written acceptance facts and observable proof. ## Remaining failure modes and decision triggers

A compact brief still relies on a correct spec, supported launch, available provider, safe environment and adequate evaluator.
