**Situation:** twice now, a design specified a rule or trigger in prose — a MUST-level standard with no gate to enforce it, and separately a README describing "the read-model regenerates on every commit via a post-commit or Stop hook" — and in both cases the actual wiring was never installed. The design looked complete (it was written down, reviewed, and referenced elsewhere as if it were live behavior) but nothing in the system actually executed it; the gap only surfaced when someone checked for the hook/gate directly.

**Lesson:** documentation that describes a trigger/enforcement mechanism is a PROPOSAL for that mechanism, not evidence it exists. A prose rule ("this MUST happen", "this regenerates on X") is trivially easy to write and just as easy to leave un-wired, because nothing fails loudly when it's missing — the system just silently never does the documented thing, and everything downstream that assumes it does (a fresh cache, an enforced standard) quietly degrades instead of erroring. This is the same failure shape whether the missing piece is a git hook, a CI gate, or a Stop-hook check — the common root is "we described the mechanism" being mistaken for "we built the mechanism."

**Apply next time:** when a doc/README/standard asserts "X triggers Y" or "this MUST happen," treat that sentence as unverified until you find the ACTUAL hook/gate/CLI call site that fires it (grep for the hook config, the CI step, the enforcing script) — absence of a gate is the default state, not an edge case. When shipping a new trigger-dependent design, ship the trigger's wiring in the SAME change as the doc that describes it, or file the wiring gap as its own tracked backlog item immediately (as BL-0052 does here) rather than leaving the doc to imply it's already live. **Also verify the documented TIMING, not just existence:** when a doc names a specific point ("check before stage 4", "runs after step N"), grep the actual call site to confirm it fires at that point and no earlier — a precondition the code exercises earlier than its own docs claim is functionally the same trap as a mechanism that was never wired at all, just discovered later and closer to production. **Also verify a documented EXEMPTION, not just a documented trigger:** a reference doc that describes a carve-out for one category ("type X is exempt from check Y") is just as easily un-wired as a positive trigger — check that the enforcing gate actually takes the category/type as a parameter it can branch on, rather than assuming a documented exemption exists just because it's written down; a gate with no such parameter enforces the same rule on every category regardless of what the reference claims.
