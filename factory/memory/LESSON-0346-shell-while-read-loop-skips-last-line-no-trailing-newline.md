**Situation:** a list of file references was written to disk by joining entries with `\n` (a common
pattern in scripting languages, which does not add a trailing newline after the last element). A shell
`while read line; do ... ; done < file` loop consuming that file silently processed every line except
the LAST one — `read` requires a trailing newline to deliver a final record, and without one the last
line is dropped with no error, warning, or non-zero exit code. The missing entry was an image copy
operation, so one asset silently went missing from the build.

**Lesson:** `"\n".join(items)` and `while read` have an impedance mismatch that fails completely silently:
the join produces N-1 newlines for N items (no trailing newline), while POSIX `read` treats a line
without a trailing newline as not a complete record and drops it. This is a classic, well-known shell
gotcha, but it reproduces invisibly whenever a list file is generated by a non-shell tool that doesn't
think in terms of "every line needs a trailing newline," and the loop body doing something silent (e.g. a
file copy) means nothing visibly complains when an item goes missing.

**Apply next time:** when generating a file meant to be consumed by `while read`, ensure every line ends
in a newline (append one after joining, or use the target language's line-writing primitive rather than
join). As a second line of defense, write any script that copies/moves files from such a list to report
every expected-vs-actually-processed count explicitly afterward, so a silently-dropped last line surfaces
as a count mismatch rather than a missing asset discovered later.
