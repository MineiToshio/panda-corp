## Problem
`plugin/skills/design/references/freeze-and-fidelity.md`'s M1 owner-status template (line 111: "Prototipo
frente a FRDs: A cosas que el prototipo tiene y los FRDs no, B al revés. Te propongo: <lista corta con la
recomendacion por punto>") frames the owner's scope-cut decision around a short recommendation list. During
the Mission Control v2 redesign, an owner scope decision ("features the prototype doesn't draw stay out
of v2") was made against a six-item list drawn from the redesign proposal document. The freeze's own
context packs (S0.3), which enumerate every acceptance criterion from the actual FRDs, later surfaced
dozens of additional undrawn ACs the proposal never mentioned — including features already BUILT AND
VERIFIED in the live product (a snapshot panel, a global accounts directory, a pending-merges indicator).

Impact: an owner confirming a scope cut against an incomplete, proposal-sourced list can unknowingly
authorize dropping already-shipped, verified functionality the list simply never named — a real risk of
silent regression through an otherwise-legitimate human gate.

## Fix plan
1. Change M1's own procedure (`freeze-and-fidelity.md` M1 row + its message template) so the "B" (prototype
   lacks what the FRD specifies) side of the comparison is always generated by enumerating EVERY
   acceptance criterion across every UI FRD against the captured states (the same mechanism S0.3/S1.3's
   DR-064 reconciliation already runs), not by reusing the proposal document's own illustrative list.
2. When an undrawn AC maps to a feature that is `VERIFIED` in the live product's work-order state (for a
   REDESIGN of an already-built app), mark that line distinctly in the owner message (e.g. "⚠ ya construido
   y verificado") so the owner sees the higher stakes before confirming the cut.
3. Keep the message's own brevity for the owner-facing summary — the change is to the SOURCE the summary is
   built from, not to make the chat message itself exhaustive; link to the full enumerated list artifact
   (e.g. `freeze/reconciliation.md`) for the complete picture.

## Tests (prove the fix — TDD, RED → GREEN)
- A fixture project where the redesign proposal names N items but the FRDs' ACs contain N+M undrawn items
  (M already `VERIFIED` in work-order state): the M1 status-generation step must surface all N+M items, with
  the M already-verified ones flagged distinctly (RED before the fix — only N items surfaced; GREEN after).

## Done when
- M1's scope-comparison source is the full FRD AC enumeration, verified by the fixture test.
- The already-verified-feature flag renders in the generated owner message.
- Plugin MINOR version bumped (new instruction-level behavior) + manifests regenerated; decision log entry.

## Out of scope
- Automatically rejecting a scope cut on an already-verified feature — the owner's decision still stands;
  this item only ensures they see the full picture before deciding.
